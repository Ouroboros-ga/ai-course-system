根据你提供的两份参考文档（命题要求与API设计规范），我们可以清晰地推导出云端存储的架构形式。
**核心结论：**
云端**不是**简单地存储一个生成的 Markdown 文件，也不是等本地请求了再临时处理。
根据 API 规范，云端采用的是 **“结构化数据+ 媒体文件对象存储（OSS）”** 的混合存储架构。
下面为你详细拆解这种存储形式的具体逻辑：
### 一、 读取完成后，文件以什么形式存储？
根据《开放API设计规范》中的接口返回数据，存储形式分为三个阶段，分别对应不同的数据形态：
#### 1. 解析阶段：存储“结构化元数据”
当课件（PPT/PDF）上传并解析完成后，系统并不存储 Markdown，而是存储**结构化的知识点树**。
*   **依据**：API `2.1.1 课件上传与解析接口` 返回的 `structurePreview`。
*   **存储内容**：
    *   文件元信息（文件名、页数）。
    *   知识点层级结构（章节数据：`chapterId`, `chapterName`, `pageRange`）。
*   **存储形式**：存入**数据库**。例如 MySQL 的 `course_structure` 表，字段包括 ID、父级 ID、名称、关联页码等。
#### 2. 脚本生成阶段：存储“结构化脚本对象”
这是“智课”的核心。系统根据解析结果生成脚本，存储的是**分段的、带属性的教学内容**。
*   **依据**：API `2.1.2 智课脚本生成接口` 返回的 `scriptStructure`。
*   **存储内容**：
    *   脚本 ID (`scriptId`)。
    *   分段内容数组：每一段包含 `sectionId`（章节ID）、`content`（讲授文本）、`duration`（时长）、`keyPoints`（重点标签）。
*   **存储形式**：存入**数据库**（如 MySQL 的 `lesson_scripts` 表），通常使用 JSON 字段存储分段数组，或者拆分为 `script_sections` 子表。
    *   *注意：这里的数据是结构化的，不是 MD 文件。这样设计是为了支持前端“教师脚本编辑功能”，方便对某一段进行修改。*
#### 3. 音频合成阶段：存储“媒体文件 URL”
音频文件体积大，不适合存数据库。
*   **依据**：API `2.1.3 语音合成接口` 返回的 `audioUrl`。
*   **存储内容**：生成的 MP3/WAV 文件。
*   **存储形式**：存入**对象存储服务（OSS/S3/MinIO）**。数据库中只存储文件的 URL 路径（如 `http://xxx.com/audio/lesson/20240520001.mp3`）。
---
### 二、 是“云端预处理”还是“本地请求再生成”？
根据命题要求，是**云端预处理**，而非本地实时生成。
**理由分析：**
1.  **性能指标要求**：
    *   命题要求“课件解析响应时间≤2分钟 / 份”。
    *   “问答响应时间≤5 秒”。
    *   如果音频是在学生点击播放时才在云端生成，学生需要等待 TTS（语音合成）处理，这会消耗掉这 5 秒的宝贵时间，导致体验极差。
2.  **教师编辑工作流**：
    *   API `2.1.2` 中提供了 `editUrl`（脚本编辑地址）。
    *   这意味着流程是：**云端生成脚本 -> 教师在线编辑/审核 -> 云端生成音频 -> 学生端播放**。
    *   如果没有在云端存储生成好的脚本和音频，教师就无法进行预审核和修改。
**因此，云端存储架构流程如下：**
1.  教师上传 PPT -> 云端解析 -> **存数据库（知识点结构）**。
2.  云端生成脚本 -> **存数据库（结构化文本）** -> 教师可编辑。
3.  云端合成音频 -> **存 OSS（音频文件）** -> 数据库存引用 URL。
4.  学生端请求 -> 云端直接返回音频 URL 和结构化数据 -> 本地播放。
---
### 三、 云端应该怎样存储？（数据库设计建议）
基于上述分析，云端数据库应设计为**关系型数据库**（如 MySQL），配合**对象存储**。以下是针对核心业务的存储表设计建议：
#### 1. 课件解析表 (`course_parse_records`)
存储原始解析结果，对应 API 2.1.1。
*   `parse_id` (主键): 解析任务 ID
*   `course_id`: 课程 ID
*   `file_url`: 原始 PPT/PDF 的 OSS 地址
*   `structure_json`: 存储解析出的章节树（JSON 格式）
*   `status`: 解析状态
#### 2. 智课脚本表 (`lesson_scripts`)
存储生成的讲授内容，对应 API 2.1.2。
*   `script_id` (主键): 脚本 ID
*   `parse_id` (外键): 关联解析记录
*   `section_id`: 章节 ID
*   `content_text`: 该章节的讲授文本
*   `key_points_json`: 重点标签
*   `duration`: 预计时长
#### 3. 媒体资源表 (`lesson_audios`)
存储音频文件信息，对应 API 2.1.3。
*   `audio_id` (主键)
*   `script_id` (外键)
*   `audio_url`: 音频文件在 OSS 的路径
*   `format`: mp3/wav
*   `file_size`: 文件大小
#### 4. 问答与进度表 (`user_learning_progress`)
存储用户的学习状态，对应 API 2.3.1。
*   `track_id`
*   `user_id`
*   `current_section_id`: 当前学到哪一段（用于进度续接）
*   `qa_history_json`: 历史问答记录（JSON 格式，用于多轮对话上下文）
### 总结
云端**不应存储 Markdown 文件**作为最终交付物。Markdown 只是文档转换的一种中间视图。
**正确的云端存储姿态是：**
*   **文本内容** -> 数据库的结构化字段中，方便检索、编辑和关联。
*   **音频视频** -> 对象存储（OSS），数据库存 URL。
*   **逻辑关系** -> 数据库的主外键关联（课件 -> 章节 -> 脚本 -> 音频）。
这样既满足了命题中“教师编辑脚本”的需求，也满足了“学生实时问答、进度续接”的高性能交互需求。
