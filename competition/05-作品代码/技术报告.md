## 1. 项目概述

### 1.1 背景

学科建设的关键挑战之一，是优质教学资源与个性化辅导供给需要持续提升。教师既要备课、出题、批改，又要兼顾个性化学情；通用大模型具备对话能力，而教学场景进一步要求权威、可追溯、可问责，并安全地支持学生真正“跑起来”科研实验。

### 1.2 赛题理解

赛题要求“学科垂类大模型 + 创新应用”，本质是两条能力线：一是**垂类化的知识与生成**（学科知识库、领域微调、可追溯 RAG），二是**面向实际价值闭环的应用**（助教 / 助学 / 助研三场景、可执行实验闭环）。本作品将两条线融合为一件事：**让面向计算机学科的大模型既“会说计算机”，也做到“查得到依据、跑得出结果、留得下证据”。**

### 1.3 CodeNexus 定位

CodeNexus 面向计算机学科教学与科研场景，围绕“课程内容建设、学生学习与练习、复杂专业任务处理、科研检索与实验验证”构建智能体平台。系统由 **Teaching Agent** 与 **Nexus AI** 两条核心能力链组成：Teaching Agent 面向课程学习与个性化教学；Nexus AI 面向跨课程复杂任务，并可切换至 **Research Mode** 开放论文检索与科研实验能力。

```text
CodeNexus
├── Teaching Agent
│   ├── 智能备课           （资料→结构→讲稿→教师审核→发布）
│   ├── 课程学习 / 问答     （Citation 闭包可追溯）
│   ├── 练习 / OJ          （Judge0 沙箱）
│   ├── Learning Evidence  （学习行为与练习结果）
│   └── RE-KT 六维认知      （掌握状态建模）
│
└── Nexus AI
    ├── General
    │   ├── Course RAG      （课程材料 → 证据）
    │   ├── CS Knowledge    （学科权威知识）
    │   ├── Web / arXiv     （补充参考，三级降级）
    │   └── Artifact        （MD / LaTeX 标记产物）
    │
    └── Research（Research Mode）
        ├── Paper Search    （arXiv 检索）
        └── NexusLab        （复现实验 + 确定性判定）
```

这张产品能力图是理解全系统的锚：**左半边是确定性教学闭环，右半边是开放式科研闭环，共享同一课程权限与证据底座。**

## 2. 需求与设计目标

### 2.1 场景需求：系统重点解决的四个问题

1. **教学内容生产提效**：教师已有教材、PPT、讲义，需要高效生成课程结构、教学内容与讲稿，并在改版后清晰追溯“讲稿依据哪份材料的哪一页”。
2. **学习过程形成连续闭环**：将问答、练习、代码执行和学习状态连接起来，形成连续、可审计的教学证据链。
3. **学科可信上下文**：教学场景要求回答基于学科可信上下文，来源可追踪，学生能够确认“这句讲解依据是什么”。
4. **科研助手推进到执行闭环**：科研助手需要从论文总结进一步推进到**真实代码执行、实验指标与可验证报告**，并让运行结果可核实。

### 2.2 设计目标与五条原则

**结论一句话**：CodeNexus 将大模型作为**调度课程知识、专业知识、代码评测、文件产物和科研实验环境的智能体执行核心**。由此确立五条设计原则：

1. **以课程为系统边界**：材料、知识、检索、问答、练习、学习证据都归属课程；模型供应商可替换，课程权限、版本与证据归属在模型切换时保持稳定。
2. **以证据评价生成内容**：生成内容须引用有效材料证据并过质量门；证据缺失时保留候选或返回明确失败语义。
3. **以版本快照管理变化**：重解析、改课程、更新图谱、重建索引均通过不可变快照、激活指针与回滚记录管理（§6.5）。
4. **以最小权限和工具自校验约束智能体**：课程访问服务先解析能力，各工具执行前再校验课程与角色，高风险动作需确认，治理不可用时 fail-closed（§10）。
5. **以证据强度区分学习数据用途**：交互信号描述过程、正式评分支持判断、完整对话服务体验、审计数据追踪运行，四类数据分别保存、授权与消费（§6.4、§10）。

### 3.2 两个关键隔离（核心设计考量）

1. **教学与科研的职责隔离**：Teaching Agent 处理确定性教学，Nexus 处理开放性科研，保持教学问答的确定性与科研探索的开放性各自清晰。
2. **Backend 与 Nexus Runtime 的运行时隔离**：

> 现有教学后端承担用户、课程、权限、知识与 Teaching Agent 等**业务真相**；Nexus Runtime 作为**独立进程**负责 Agent Loop、Context、Checkpoint 与工具调度，通过受控 HTTP 接口（HTTP Tool Adapter）调用现有业务能力，**保持新一代 Agent 与原有教学系统依赖解耦**（新旧 LangGraph 依赖树相互独立）。

**trade-off**：为兼容旧 Backend 稳定教学的 LangGraph 0.6 与 Nexus 新生态，系统采用独立运行时，以“一次进程间通信”的代价，换取**边界清晰、升级互不影响、失败可隔离**。

### 3.3 数据与安全底座

- PostgreSQL 16 + pgvector（生产基线，Alembic 显式迁移）+ LanceDB 向量索引（`course-lancedb/1.0`）；本地 SQLite。
- 代码执行两级沙箱：学生题目级 → Judge0；未知科研仓库 → Repro Worker，未配置 **fail-closed** 时不进入主进程（§10.3）。

## 4. 智能备课与 Teaching Agent（教师端到学生端闭环）

### 4.1 教学闭环

```text
教学资料 → 解析 → 课程结构 → 课件/讲稿 → 教师审核 → 发布
                                                        ↓
                                   Teaching Agent（问答/练习/OJ）
                                                        ↓
                                    Learning Evidence → RE-KT 六维认知
```

**关键立场：教师拥有最终审核权。** AI 输出以**草稿/提案形态**存在，经教师批准后进入正式课程或题库；发布后对 AI 再锁定。正式发布前始终保留教师审核环节。

### 4.2 智能备课双门控

约束 AI 备课的两道**硬门**由代码强制：

1. **证据门（evidence_refs 校验）**：备课输出经 `_assert_evidence_ids` 递归校验所有 `evidence_refs` 是否可解析到当前课程有效证据，未知 ID 抛 `StructuredOutputError` 触发重试——**无效引用在写入前被拒绝**（`services/controlled_prep_workflow.py`）。
2. **锁定节点保护**：`_filter_operations` 丢弃命中已发布/锁定节点的操作；操作白名单只允许改**非锁定节点的标题与脚本内容/风格**，禁止增删移节点（`services/course_prep_agent_service.py`）。

**代码索引。** 上两文件 + `platform/agents/prep/validation.py`（增量白名单）。

### 4.3 Teaching Agent：可追溯问答与认知闭环

- **25 节点 LangGraph 工作流**（`platform/agents/edu/workflow.py`）：证据检索、学科参考、意图路由、教学动作策略；回答受 Citation 闭包约束（§6.2），证据不足改写“课程证据不足”。
- **六维认知（RE-KT）闭环**：学习行为与练习结果形成学习证据 → 六维掌握建模（§6.4）→ 驱动学习路径规划、练习/测验推荐与前置补学 → 再反哺备课出题。**RE-KT 归属教学侧，Nexus 专注跨课程复杂任务与科研闭环。**

## 5. Nexus AI Agent Harness（技术核心）

### 5.1 设计动因：从路由式调用到 Agent Loop

路由式实现适合“意图 → 单动作 → 单工具 → 回答”：

```text
Intent → Action → Single Tool → Response
```

Nexus 面向**持续多步推理、跨轮长任务、失败恢复与上下文压缩**，采用标准 Agent Loop：

```text
Goal
 → Model(LLM)
   → Tool 调用
     → Observation
       → Model
         → Tool …
         → Answer / Artifact
```

**trade-off**：采用 **Deep Agents** 作为 Agent Harness，基于 **LangGraph 持久化执行状态**，支持连续 Tool Loop、长上下文压缩（Context Compact）、Streaming、Checkpoint 与跨轮会话恢复。为保持与旧教学依赖解耦，Nexus 以**独立 Python 项目（独立 venv / pyproject / 锁文件）**运行于独立进程（§3.2），经 HTTP Tool Adapter 调用后端业务。当前定位是“多工具、长上下文、可恢复 Agent Runtime”，并持续扩展工作区能力。

### 5.2 Agent Loop 与 Harness 能力

| 能力              | 说明                                | 验收          |
| ----------------- | ----------------------------------- | ------------- |
| Tool loop         | 多工具循环                          | NX-E2/E3      |
| Context Compact   | 长上下文全图压缩，防溢出            | 边界保留      |
| Checkpoint / 恢复 | checkpoint 持久化 + 前端 cold 恢复  | NX-E1         |
| 取消语义          | 取消→回收→幂等→已完成步骤保留       | NX-E3         |
| 有界日志脱敏      | 20/40 行有界、8000 字符上限、真脱敏 | Worker v0.3.0 |

### 5.3 工具面与能力收敛

- **工具面（2026-09-09 实测）**：General 7 工具（web_search / search_course_materials / search_cs_knowledge / write_artifact / read_attachment / write_todos / read_file）；Research 扩展至 19（含 search_arxiv_papers、collect_paper_evidence、plan/run/cancel/get_reproduction_run、request_reproduction_approval 等）。
- **effective capability 过滤**：仅当 `注册面 ∩ 模式 ∩ 工具面 ∩ health/config ∩ 权限` 均满足时，工具才展示为可用并执行。
- **文件最小权限**：文件系统中间件白名单仅暴露 `read_file`；写入、目录枚举与执行能力均不开放。

**代码索引。** `nexus/src/nexus/agent.py` · `platform/agents/providers/governance/tool_governance.py`。

## 6. 多源知识与可信 RAG

### 6.1 多源与来源分级

| 源               | 内容                                                         | 角色                                     |
| ---------------- | ------------------------------------------------------------ | ---------------------------------------- |
| **Course RAG**   | 课程材料解析为带 Evidence ID 的结构化证据                    | 课程当前事实（墨蓝“依据”），回答主事实源 |
| **CS Knowledge** | `knowledge_data/` 11 门核心课 112 节点/106 关系，锚定权威教材/标准 | 权威定义（琥珀“学科参考”）               |
| **Web / arXiv**  | SearXNG/DDG 三级降级、arXiv 接口                             | 外部补充参考，固定 `is_supplementary`    |

角色边界：课程证据与学科参考冲突时**以课程证据为准**（prompt `teaching-agent-prompts/1.5`）。

### 6.2 Citation 闭包与失败关闭（RAG 核心创新）

1. **证据字符级锚定**：材料经 Docling/OCR 解析为 `EvidenceSpan`，具四层稳定 ID（artifact/document/unit/block）+ 原文定位（page_or_slide/char_start/char_end）+ 状态机（ACTIVE/STALE/SUSPENDED）；引用密钥 = `SHA-256(artifact|block|char_start|char_end)[:12]`，证据缺失返回 `None`，保持真实来源。
2. **回答级验证**：`validate_response` 强制答案中每个 `evidence_id` 属于本次检索结果集——伪造引用被剔除；严格约束下清空引用并改写“课程证据不足”。
3. **检索三重闭合**：课程隔离（`has_active_release`）、版本一致（绑定发布冻结快照 ID）、Citation 闭包（`citation_closed` 标记）。
4. **失败关闭**：向量/知识包不可用返回 `COURSE_RETRIEVAL_UNAVAILABLE`；系统保持课程隔离、版本一致，仅使用已审核内容。
5. **过期证据分栏**：重解析后旧证据标记 STALE 并保留，`EvidenceBundle` 分栏，可回看“当时依据了什么”，主链路只走激活快照。

**代码索引。** `platform/evidence/contracts.py` · `evidence/citation.py` · `platform/retrieval/providers/canonical_document_ir.py` · `platform/agents/edu/workflow.py` · `services/document_parse_service.py`。

### 6.3 检索融合：三条技术原则

1. **Course Scope**：课程资料检索必须基于用户权限（Course Access 能力视图），保持课程边界清晰。
2. **来源分级**：课程材料、CS Knowledge 为内部可信来源；Web 为补充来源（§6.1），层级清晰。
3. **采用来源分级与相关性决策（关键决策）**：

> 系统分别召回候选证据，再根据问题相关性决定上下文如何使用——避免“题目问神经网络，却用课程材料加权压制通用知识”的误配。

### 6.4 双源证据分层与六维认知（RE-KT）

**机制。**

1. **证据准入分层（写入路径硬约束）**：正式 `LearningEvidenceRecord` **仅接受服务端评分及聚合服务写入**（客观题评阅、Judge0 终态聚合），学生提交分数不进入正式证据；交互信号只进 `LearningEvent`/投影，不构成掌握结论。
2. **六维认知向量** `s(c,k)=⟨performance, confidence, confusion, depth, hint, need⟩`：
   - 表现分 = 加权窗口均值（窗口 5，权重门槛 3.0；代码证据权重 1.5 > 测验 1.0）；
   - 置信度 = `w/(w+3)`；困惑 = `0.7×错误率 + 0.3×重复因子`；
   - 解释需求 = `0.5×confusion + 0.3×(1−perf) + 0.2×hint`（驱动“该不该讲解、讲多深”）；
   - 掌握分层 ≥0.8/≥0.6/≥0.4 → advanced/proficient/developing/beginner。
3. **显式未知与原因码**：证据不足维度保持 `unknown` 并记录原因码（`no_attempt_data` 等），确保结论可解释。
4. **认知衰减**：置信度半衰期衰减；路径判弱要求表现分<0.5 且样本≥3 且衰减后置信度≥0.6。
5. **episode 聚合抗刷分**：一个 guided session 多次运行**只聚合为一个证据 episode**，一次 episode 只写一条证据；反馈层明示“这是练习证据，不单独判定掌握”。

**理论定位**：相较输出单一掌握概率的经典知识追踪（BKT/DKT/IRT），本设计选择**面向教学决策的可解释性优先于预测精度**——六维对应教师真实关心的六个判断维度；置信度收敛式是贝叶斯更新的工程简化；半衰期衰减对应间隔重复的遗忘曲线结论。`rule_baseline` 为当前确定性实现，BKT/DKT 等数据驱动估计器留有清晰接口，升级时保持既有可审计链路。学术定位上，RE-KT 属于**证据驱动的、面向教学动作的学习者状态模型**——依据不同可信度证据输出六维状态，而非追求单一"下一题预测概率"；与学习型知识追踪（DKT/AKT/simpleKT）的公平对照见附录 A.4。

**代码索引。** `services/cognitive_service.py` · `coding_challenge_service.py`（`close_session`）· `cognitive_decay_service.py` · `learning_path_service.py`。

### 6.5 不可变版本快照

以“不可变快照 + 激活指针 + 回滚记录”统一四域：课程发布（`CourseRelease`，回滚=创建新 Release）、知识图谱（`GraphSnapshot`，SUPERSEDED/ROLLED_BACK）、向量索引（LanceDB staging→Bundle 激活）、媒体资产（修改新建版本，旧版 stale）。配合 §6.2 版本绑定，保证**任何回答对应明确发布版本、任何回退不损失历史**。

### 6.6 学科垂类模型：领域 SFT 微调（垂类化双轨之二）

垂类化由两条腿构成：**RAG 解决"查得对"，领域微调解决"说得专业"**。本节聚焦生成侧的能力打磨。

**基座与架构理解。** 默认基座为 **Spark-X2.5-4B**（4.11B dense，36 层，Apache-2.0 可商用）：采用**混合注意力**（每 4 层中 3×sliding-window 512 + 1×full attention）、**GQA（16Q/4KV）**、原生 1M 上下文。其架构存在一个对工程适配有要求的特点：**注意力将 QKV 融合为单一 `q_k_v_proj` 并有门控 `g_proj`，没有标准的 `q_proj/k_proj/v_proj/o_proj`**——LoRA 目标模块须按 `model_type` 自适应精确定位，投影名匹配不当将导致目标模块零命中。本管线据此实现类型分发（spark 系 `q_k_v_proj,g_proj,out_proj,gate_proj,up_proj,down_proj`；Qwen/LLaMA 系回退标准投影），确保目标模块精确匹配的工程严谨性。

**训练数据（防污染设计）。** v3 指令集 **3127 训练 + 231 评测**，类型覆盖 `node_explain/definition/keypoints/example/paraphrase/compare/clarify/kp_qa/multiturn/teach/quiz/rel_forward|reverse|judge_*/safety`；**防污染红线：评测基准 10 问只进 eval 集不进训练集**（进训练则微调收益只是记忆而非泛化），并自动扫描知识库节点文件，新增课程无需改脚本。

**真实训练与产出。** 在 4090 24GB 上完成 LoRA 训练（3 epochs / 588 步 / 26 分钟，梯度检查点，QLoRA 4bit 降级可选），交付 140MB adapter（7 文件，SHA256 记录）+ 588 点逐步 loss 曲线。训练收敛良好（train_loss 0.2032）；同分布 eval 侧**困惑度由基座 10.98 降至 1.057**，直观体现生成侧向学科口径与讲师风格收敛。

**技术口径与定位。** 在防污染基准上，严格 markers 自动判定覆盖 8 题，基座与 LoRA 均通过 4 题；收益集中体现于**同分布拟合与学科风格贴合**，而非基准短答的通过数差异。据此，本报告将微调价值定位于"**课程口径贴合 + RAG 生成双轨形成垂类闭环**"，评测原始判定在同目录 `evidence/` 记录中完整可回溯。

**代码索引。** `backend/finetune/train_lora.py` · `data/prepare_dataset.py` · `evaluate.py`；交付 `competition/05-作品代码/model_spark_x25_4b/`。

## 8. NexusLab 与 Quick Reproduction

### 8.1 设计原则

大模型负责生成实验建议，实验结果必须来自真实执行。若“复现成功”由 LLM 口头总结，“成功”将缺乏可验证依据。CodeNexus 采用三角色分工原则：

```text
LLM      负责：规划 / 选择 / 解释
Worker   负责：真实执行
Verifier 负责：最终判定（确定性指标，非 LLM）
```

### 8.2 三问分离 + 真实流程

| 问题       | 机制                                                         |
| ---------- | ------------------------------------------------------------ |
| “能不能跑” | **preset 白名单**：`plan_reproduction` 只匹配人工核验预设，未命中返回 `no_preset`，禁止现场编造命令 |
| “该不该跑” | **审批票据**：无票据只建提案不执行；`consume_approval` 原子核销，绑定 user/session/run/plan 哈希/预算/有效期，**一次批准一次执行，不可重放** |
| “跑没跑成” | **数值阈值**：PASS/FAIL 由确定性程序数值比较，LLM 不参与判定 |

真实流程（当前比赛版为**受限的 Verified Preset Reproduction Runner**，支持经人工核验预设的复现）：

```text
Nexus Research → plan_reproduction → Verified Preset → run_reproduction
 → Independent Repro Worker → 真实命令执行 → Metric Extraction
 → Deterministic Verification → report.md / report.json
```

### 8.3 nanoGPT 真实实验

```text
Repository: karpathy/nanoGPT   License: MIT
Expected:  val_loss = 1.88 ± 0.06
Actual:    val_loss = 1.8857
Result:    PASS
```

> PASS/FAIL 由确定性程序进行数值比较，LLM 不参与判定。（线上 job `c3e71851e513`，5 步 succeeded，report.md/.json 落库；证据 `docs/phase1/验收记录/M4_验收_2026-09-05.md`）

**独立 Repro Worker 的设计理由**：学生 OJ 的 Judge0 面向**单题编译运行**；论文仓库属于**更高风险的仓库级执行场景**，因此科研复现放入独立 Repro Worker，通过资源配额、超时、License 校验和最小结果回传降低执行风险（资源配置：CPU、900s 总时长、单步 300s、磁盘 2GB、并发 1、超时 SIGKILL）。

**代码索引。** `nexus/src/nexus/tools/reproduction.py` · `deploy/repro-worker/worker.py`。前端 NexusLab 以研究对话+实验视图一体化呈现运行状态卡、PASS 绿/FAIL 红徽章、“非 LLM 判定”标注。

## 附录 A　相关研究与方法定位

> 本附录将系统所选技术路线与近五年的公开研究做对照，用于说明"选择"的依据，不构成对基础方法的原创性主张。所有"评估方向"均为后续工作，非当前已实现能力。

### A.1 总体定位：四条研究线交叉处的系统工程

本系统处于 **LLM Agent、可信 RAG、知识追踪、参数高效微调** 四条研究线的交叉点上。就现有证据而言，系统的说服力主要来自**系统工程组合创新**——"版本绑定证据闭包 + 分层学习证据 + Agent capability 治理 + 一次性实验审批 + 确定性验证器"的组合，而非 RAG、Agent Loop、LoRA、知识追踪等单一基础方法的原创。报告正文凡涉及"核心创新"的表述，均限定到本系统的具体机制。

### A.2 可信 RAG：从"来源闭包"到"语义支持"（研究定位）

系统当前的 Citation Closure 解决的是**来源闭包**：所有输出引用都来自授权、当前版本、本轮检索结果集，形式化为 `C_output ⊆ R(q, u, c, v)`——有效阻止模型凭空构造证据 ID。ALCE 已指出"生成了引用"与"引用足以支撑回答"是不同维度，RAGAS/ARES 亦将 context relevance 与 answer faithfulness 分开评估；据此，系统的**评估方向**（后续工作计划）是把指标拆分为引用合法率、引用蕴含（entailment）与引用完整性三级，并引入独立于生成 LLM 的语义支持校验器（推荐"规则/小型 NLI + 独立 judge + 教师抽检"三级，而非单一 LLM 自评）。课程不可用的失败语义则与 Corrective RAG 的"检索质量不可靠时显式纠正/降级"思路一致。

### A.3 Agent 与安全研究对照

- **Agent Loop**：Nexus 的 `Model→Tool→Observation→Model` 属 AgentBench/ReAct 追踪框架的工程化实现；系统的差异化落在**持久执行（checkpoint/resume）、上下文压缩（Context Compact）与课程/科研领域约束**，而非 Agent Loop 本身。
- **安全边界**：Agent-SafetyBench 与 InjecAgent 表明工具型 Agent 的越权与间接 Prompt Injection 不能仅靠语言层防御。系统据此把安全边界落在 **effective capability 过滤、工具级自校验、一次性审批票据与独立执行沙箱**（capability/tool-broker/approval/sandbox 层），而非依赖 system prompt；Web/arXiv/课程材料均按"不可信数据进入高权限 Agent"处理。**评估方向**：引入面向本系统场景的注入对抗子集，验证即使 LLM 尝试调用，运行时边界仍不可跨越。

### A.4 知识追踪：RE-KT 与学习型基线的对照定位

RE-KT 的价值不在"预测下一题概率"，而在**可解释 + 教学动作导向**。为论证其不弱于学习型基线，**评估方向**是：在统一预处理与 student-level split 下，与 BKT / DKT / AKT / simpleKT 对比 AUC、校准（Brier/ECE）、冷启动与教学干预效用；pyKT 提供现成的公平比较底座。研究同时提示 KT 的"解释"本身向教师是否有用仍需验证，因此**评估方向**还应包含教师实验（给定六维状态 vs 单一概率，比较教学判断正确率、决策时间与一致性）。

### A.5 可信执行与复现（四级语义）

大模型可生成实验建议，但"复现成功"须由真实执行与确定性验证给出（§8）。参照研究建议，系统后续将"能否复现"拆为可追溯的**四级语义**：`executed`（确实运行）→ `metric-reproduced`（指标达标）→ `result-reproduced`（结果一致）→ `conclusion-reproduced`（结论成立）。当前 nanoGPT 实验已具备前两级（真实执行 + `val_loss=1.8857` 对阈值判定 PASS）；后续将保存多次 seed 并报告 mean/σ/95%CI，使"跑过一次"提升为"同一快照重复运行统计一致"。
