## 1. 核心问题与设计主线

### 1.1 场景与真实问题

CodeNexus 面向计算机学科的教学与科研两个场景，两端各自存在被工程实践反复验证的痛点：

**（P1）教学内容生产割裂。** 教师已有教材、讲义、PPT，但从资料到结构化课程（章节树、讲稿、习题）的过程重复性高；引入 LLM 辅助后，生成内容无证据约束、无结构边界，教师审校成本反升。

**（P2）学习过程缺少连续闭环。** 通用问答系统"回答即结束"：练习结果、代码执行、提问行为无法沉淀为可解释的学习状态，"掌握度"要么缺失、要么只是一个黑箱概率。

**（P3）通用模型缺少学科可信上下文。** 直接依赖模型参数知识，会出现课程口径错位、出处不可核验——模型可能为"课程里讲了 X"编造一个页码，而教师无法查证。

**（P4）科研助手停留在"回答"层面。** 现有科研 AI 能总结论文，但"复现成功"若由 LLM 断言，不具备科研可信性；真实实验需要真实执行、真实指标与可复核判定。

### 1.2 核心矛盾

四个痛点背后是同一个矛盾：**大模型天然是生成器，而严肃学科场景要求输出可溯源、执行可验证、结论可解释——生成本身不提供这三项保证。** 若靠提示词约束，模型可被绕过；若靠事后人工抽查，规模不可扩展。

因此 CodeNexus 的全部设计收敛为一句话：**让面向计算机学科的大模型既"会说计算机"，也做到"查得到依据、跑得出结果、留得下证据"**——且三项保证由数据结构与流程机制兑现，而非由提示词承诺。

### 1.3 本文贡献

1. **一套从来源到结论的信任闭环机制**（§3–§4）：证据基元四层寻址 + 引用密钥闭包 + 备课双门控 + 发布快照冻结，把"有据可说"变成可验证的数据性质。
2. **一套把开放科研任务接入可验证执行链的运行时设计**（§6）：Deep Agents Harness 承载持续工具循环，一次性审批票据 + 独立受限 Worker + 确定性判定，把"复现成功"落到真实数值。
3. **一套模型学科化的双轨方案**（§5）：领域 SFT 对齐学科语言口径；六维认知状态使"掌握度"可解释、可被教师行动消费，而非黑箱概率。

三组机制共同回答同一个问题：**当生成来自不可天然信任的模型，系统如何通过机制而非提示词，把可信、可验证、可解释变成可兑现的设计。**

### 2.2 两条业务闭环

- **教学闭环**：课程资料 → 解析为证据 → 备课双门控生成 → 教师审核发布（快照冻结）→ Teaching Agent 问答/练习/Judge0 代码挑战 → 学习证据 → 六维认知 → 教学动作反馈回备课。
- **科研闭环**：论文检索（arXiv 三级降级）→ 复现规划（preset 白名单）→ 一次性审批票据 → Worker 受限执行 → 指标回传 → 确定性判定 → 报告 Artifact 落库。

### 2.3 两个隔离（设计取舍）

**业务职责隔离**：TeachingAgent 是课程内固定工作流（25 节点 StateGraph），本质是"能检索到精确知识的教学问答"；Nexus AI 是课程外全局入口，承载开放任务的多轮拆解与持续执行。两者不共享可变状态，仅通过 Port/HTTP 协作。

**运行时隔离**：旧 Backend 承载用户、课程、权限、证据等**业务真相**，运行于既有 langgraph 0.6 环境；Nexus Runtime 为独立 uv 项目（独立 `pyproject.toml`/`uv.lock`/venv/进程），基于 `deepagents>=0.7.12` + LangGraph 新版本树（`langchain-openai>=0.3.0`、`langchain-deepseek>=1.1.0`、`langgraph-checkpoint-postgres>=3.1.2`），通过受控 HTTP/SSE 调用旧业务能力。取舍动机：新一代 Agent 生态与既有教学链路的依赖树互不污染，任何一侧的升级失败都不波及另一侧。

**部署形态（2026-09-12 实测）**：单宿主机 `103.36.223.177`，三个 systemd 常驻服务 `smartcarb-backend`/`nexus-runtime`/`repro-runtime` 全部 `active`；容器级隔离运行 Judge0 四容器（server/worker/redis/db）、`nexus-searxng`、`smartcarb-paddleocr`、`smartcarb-postgres`（PostgreSQL 16 + pgvector）、`repro-worker`（healthy）与任务级执行容器实例。

## 3. 机制一：生成溯源——证据模型与可信 RAG

> 问题：模型引用的课程出处无法核验（P3）。若引用只是"看起来像"的文本，教师无法查证，学生无法回读。因此系统把"引用"从生成文本的一部分，改造为**可寻址、可校验、随发布冻结的数据对象**。

### 3.1 证据基元：四层寻址的 EvidenceSpan

系统把一切课程材料解析为统一的证据基元（`backend/app/platform/evidence/contracts.py`，`EvidenceSpan`）：

```text
EvidenceSpan = ⟨artifact_id, document_id, unit_id, block_id⟩
               + version_ref / page_or_slide / char_start / char_end
               + text_snippet / score / status / metadata
```

- **四层 ID**：`art_*`（源材料）→ `doc_*`（文档 IR）→ `unit_*`（结构单元）→ `block_*`（内容块，含 ContentBlock/TableBlock/FormulaBlock）。引用必须落到具体 block，不允许"文档级"的孤儿证据。
- **字符级定位**：`char_start/char_end` 与页码、bbox 并存，使学生端可从引用一键跳回原文位置。
- **内容指纹**：块与片段写入时计算 `content_hash = SHA-256(text)`，重解析后可精确判定证据是否过期。

**状态机**（数据库层 `document_parse_service.py`）：

```text
CANDIDATE ──教师确认──▶ CONFIRMED（生成正式 CourseEvidenceRecord + EvidenceCitation）
   │                        │
   ├─拒绝──▶ REJECTED       ├─材料重解析──▶ STALE（Citation → SOURCE_UPDATED）
   └────────────────────────┴─源文件失效──▶ ORPHANED（Citation → SOURCE_INVALID）
```

解析服务（`DocumentParseService`）以 `ParsePipeline.FULL` 运行，`StaleStrategy.MARK_STALE` 默认不物理删除——旧证据被标记而非消失，审计链完整保留。学生端读取（`list_citations`）默认只返回 `student_visible=True` 且状态为 `EXACT/APPROXIMATE` 的引用；教师可带 `include_stale` 查看全量。

### 3.2 引用闭包：citation_key 的确定性

引用的防伪造核心在 `backend/app/platform/evidence/citation.py`：

```python
citation_key = SHA-256(artifact_id | block_id | char_start | char_end)[:12]
```

三条硬规则直接写在实现中：

1. **无 block_id 即返回 `None`**——系统绝不为一处无法定位的引用伪造密钥；
2. **输入相同必得相同 key**——同一证据在任何回答、任何时间点生成一致的引用标识；
3. **验证契约五态**（`CitationStatus`）：`VERIFIED / PARTIAL / MISMATCH / STALE / NO_EVIDENCE`，其中 `NO_EVIDENCE` 强制 `abstain=True`——检索不到证据时回答层带弃权标记，而非无据作答。

闭包在**检索层**形成而非生成后补救：`CanonicalDocumentIRRetriever` 的每个返回块携带

```python
metadata = {
  "bundle_id": ..., "graph_snapshot_id": ..., "vector_index_id": ...,
  "evidence_ids": [...], "citation_ids": [...],
  "citation_closed": bool(item.citation_ids),   # 块是否落在证据闭包内
}
```

即进入 LLM 上下文的检索块本身即声明"我是否闭包于已核验证据"，下游无从凭空捏造一个不在闭包内的出处。

### 3.3 检索管道：三段式 fail-closed 调度

课程一旦发布，若检索仍可回退到草稿或旧索引，同一问题在不同时刻会得到不同答案——版本漂移直接破坏教学可信。因此检索调度被设计为**默认拒绝而非尽力返回**：统一入口 `RetrievalGateway`（`platform/retrieval/gateway.py`）执行严格的三段调度：

```text
① CanonicalDocumentIR（active bundle → LanceDB 向量检索）
        │ 命中 → 返回（携带 evidence_ids/citation_ids/citation_closed）
        ▼ 未命中
② has_active_release(course)？
        │ 是 → 返回空（fail-closed：已发布课程不允许回退到旧索引）
        ▼ 否
③ legacy TreeRetrieverProvider（兼容未迁移课程）
```

关键参数与实现：

- `top_k` 默认 5、硬上限 100（`_MAX_TOP_K`）；LanceDB 侧 `search_evidence` 默认 `top_k=6`，支持 `node_keys` 限定检索范围。
- 向量检索经 `ActiveKnowledgeBundle` 五元组绑定：`⟨bundle_id, version, graph_snapshot_id, retrieval_snapshot_id, vector_index_id⟩`——检索永远运行在明确的发布版本上。
- 过渡期 chunk 采用稳定 ID：`stable_chunk_id = SHA-256(scope|node_path|content[:160])[:16]`。
- 旧路径打分采用词频计数 + CJK 单字切分（单 token 非 ASCII 长串按字符切分），不伪造页码与章节 ID。

**设计取舍（多源融合）**：系统不做 `score = 0.7×course + 0.3×web` 式静态加权——静态加权等于人为预设"课程内容永远更重要"，在概念辨析类问题上反而压制正确答案。实际做法是**来源分级 + 相关性决策**：三路独立召回，把来源权威性（`authority_label`）作为元数据交给模型按问题相关性裁决。

### 3.4 发布冻结：检索快照与版本一致

教师改稿不应改变已发布版本的学生体验——这是"引用可回跳"成立的版本前提。实现方式不是锁定文件，而是发布时冻结一整族快照（`CourseRelease`）：

```text
CourseRelease = { structure_snapshot, scripts_snapshot, page_mappings_snapshot,
                  media_snapshot, graph_snapshot_ref, evidence_refs,
                  material_version_ids, document_ir_run_ids, corpus_snapshot_id,
                  retrieval_snapshot_id, knowledge_bundle_id }
```

其中 `CourseRetrievalSnapshot` 区分 `candidate`（构建中）与 `release`（发布冻结），冻结内容为 `retrieval_chunk_ids + evidence_anchor_ids` 白名单——**学生端可检索的块集合在发布那一刻封闭**。此后教师修改草稿只影响 draft，学生问答永远可回溯到"哪个发布版本、哪些证据块"。

### 3.5 多源分级：三类知识源的真实边界

三类知识源的可信度天然不同——把课程讲义与匿名网页平均化，等于把"事实"与"参考"混为一谈。因此融合策略的第一步不是打分，而是**给每个来源显式标注权威等级**：

| 来源 | authority_label | is_supplementary | 边界 |
|---|---|---|---|
| 课程资料（经 bundle/LanceDB） | 课程资料（经核实） | `false` | 可直接支撑回答与引用 |
| CS 学科知识库 | CS 语料参考（补充，需核对原文） | `true` | 补充上下文，不作课程事实 |
| Web 检索（Nexus） | 网络检索（补充参考） | `true` | 默认禁用；启用后仍受预算与 fail-closed 约束 |

WebResearch（`backend/app/services/web_research_service.py`）的硬边界全部代码化：默认 `enabled=False`（返回 `DISABLED`）；每查询预算超限返回 `BUDGET_EXCEEDED`；Provider 强制 HTTPS、超时 `httpx.Timeout(8.0, connect=3.0)`；结果序列化强制携带 `is_supplementary=True` 与 `cannot_modify_mastery / cannot_modify_recommendation / cannot_modify_graph`——外网信息**结构上无法**写为掌握度、推荐或图谱事实。

**机制证据**：`backend/tests/` 下 `test_controlled_prep_workflow.py`、`test_prep_evidence_binding.py`、`test_discipline_knowledge.py`（13 passed）等覆盖证据门与来源边界；zsitai.xyz 在线问答可直接核验引用跳转。

## 4. 机制二：教学闭环——备课双门控与代码评价

> 问题：备课产出的每个字都要经教师审核，但 LLM 自由文本无法直接进入课程结构（P1）；学生代码绝不能进入主应用进程（安全红线）。因此系统把"生成"约束为**经校验的操作集**，把"执行"隔离到**独立沙箱**。

### 4.1 证据门：递归校验的 `_assert_evidence_ids`

备课 Agent 的每次结构化输出都经过证据门（`controlled_prep_workflow.py`）：

```python
allowed = {item.evidence_id for item in evidence}   # 本次请求传入的合法证据集合
visit(model_dump())                                  # 递归遍历输出的任意嵌套 dict/list
  → 收集字段名 ∈ {evidence_id, evidence_ids, evidence_refs} 的全部值
unknown = found - allowed
if unknown: raise StructuredOutputError(...)
```

三个工程要点：**任意深度**——不依赖输出 schema 的固定形状，模型把证据引用藏在任何嵌套层级都会被遍历捕获；**两种形态**——单字符串与列表均处理；**硬失败**——出现未知证据 ID 直接抛异常进入重试，而非静默剔除（静默剔除会让模型以为引用成立）。该门在 `plan_outline`、`write_script`、`write_scripts_batch`、`verify_script` 四个产物点全部生效，并被 `PrepPlanValidator.validate_initial_output` 复用。

### 4.2 锁定节点保护：操作白名单与结构安全规则

第二道门（`course_prep_agent_service.py`）把 LLM 输出收敛为受验证的 `AgentOperation` 流：

```python
AgentOperation = { target_kind ∈ {outline, script}, target_id,
                  operation ∈ {replace, move, reorder, remove},
                  field, after, parent_node_id, order_index,
                  reason (必填 1–2000 字), evidence_refs (≤50) }
```

`_filter_operations` 的真实规则：

- `field` 按目标限制：outline 只许改 `title`，script 只许改 `content/style`——**AI 无法增删移动节点、无法触碰已发布内容**；
- 锁定匹配以 `f"{target_kind}:{target_id}"` 为键，命中 `locked_targets` 即排除（进入 excluded 清单，前端可见被拒原因）；
- 输出值等于当前值视为 no-op 跳过（不计入 discarded，避免虚假变更量）；
- `evidence_refs` 只保留合法集合内的 ID。

结构整理模式（`_filter_structure_operations`）额外实现硬安全规则：禁止删除包含锁定节点的分支；删除父节点前必须先移出全部子节点；禁止把节点移入即将被删除的父节点；**父链成环检测**；禁止对同一节点同时修改与删除；脚本关联的锁定节点不可删。

两条路径的拒绝语义刻意不同：旧 Service 路径**静默过滤**（面向教师 UI 的宽容），新 Agent Runtime 的 Incremental 路径（`prep/validation.py`）**硬拒绝**（`ValueError` 带 `target_id` 明细）——Agent 审计要求可解释的拒绝而非静默吞操作。

### 4.3 结构化重试与大纲恢复链

一次 LLM 结构化失败不应让整个备课流程归零，但重试也不能掩盖系统性错误。因此重试被限定为**带错误回灌的有限修复**（`_call_llm_with_retry`，`_LLM_MAX_RETRIES=1`）：仅 `ValidationError/JSONDecodeError/ValueError` 触发一次修复重试，修复提示**回灌具体校验错误**（"只返回符合 JSON Schema 的 JSON，不要 Markdown…校验错误：…"）；网络/认证异常不重试；两轮失败抛出用户可读的 `CoursePrepAgentPlanningError`。

大纲阶段（`ControlledPrepWorkflow.plan_outline`）实现四级恢复链，保证备课流程**永不因 LLM 单点失败而中断**：

```text
结构化输出合法 ──失败──▶ compact skeleton retry（带骨架约束重试）
     │ 大纲超预算            ──▶ 紧凑骨架重试
     ▼ 无知识点
deterministic leaf backfill（确定性叶节点回填）
     │ 仍完全失败
evidence segment 标题确定性编译骨架（纯规则，零 LLM）
```

### 4.4 代码评价：Judge0 沙箱唯一出口

学生提交的代码是不可信输入：正确答案与死循环、内存炸弹、探测文件系统的脚本在提交时不可区分，主进程执行意味着单次提交即可拖垮服务。因此执行被收敛为 Judge0 沙箱的唯一出口，且评价结论只取自沙箱真实回传（`backend/app/domain/oj/judging/providers/judge0.py`）：

- `SandboxClient` 是 **Judge0 的唯一 HTTP 出口**（类注释即此声明），支持 authn/authz 双令牌头；
- 语言白名单显式映射 10 种：`python3(71)/c(50)/cpp(54)/java(62)/javascript(63)/go(60)/rust(73)/csharp(51)/ruby(72)/php(68)`，白名单外语言直接 `ValueError`；结果文本上限 `MAX_RESULT_TEXT_CHARS=100_000`；
- 每提交施加资源限制（`cpu_time_limit/memory_limit/wall_time_limit/max_processes/max_file_size`，默认取自配置），异步提交后轮询；
- **降级语义**：沙箱未启用/连接失败/超时/内部错误统一落到 `SubmissionStatus.SANDBOX_UNAVAILABLE`——学习主流程正常降级，绝无"假造执行成功"。该枚举与 `ACCEPTED` 并列于同一状态机，意味着"沙箱不可用"与"答案正确"是互斥的可观测状态。

### 4.5 TeachingAgent 工作流与工具治理

教学动作（出题、提示、重讲、推荐）都是高风险操作：一次被诱导的越权工具调用即可触达未授权课程数据或污染学习状态。因此 TeachingAgent 不做成自由 Agent，而是**固定工作流 + 每次工具调用前治理检查**的组合——顺序确定性由工作流保证，自主性被收敛到治理边界内。`platform/agents/edu/workflow.py` 的 `build_teaching_workflow(tools)` 以 LangGraph StateGraph 编排 **25 个节点**（`add_node` 计 25 处），覆盖会话上下文加载、请求校验、安全检查、意图识别、概念解析、教学约束解析、对话历史、学生状态、认知状态、图谱上下文、题库、出题等教学前奏，再到检索增强回答与教学动作。

每个工具调用前经过 `_governance_check`：`web_research` 在课程配置 `external_research=disabled` 时直接拒绝（`TOOL_BLOCKED_BY_HARDNESS`）；通用禁用工具表内命中即拒；调用 `tool_governance.is_tool_enabled(course_id, tool_name)` 做 per-tool 策略校验；每次调用经 `_record_invocation` 写审计（输入/输出摘要、耗时、降级标记、策略判定）。治理端口异常时低风险工具 fail-open 放行，高风险路径 fail-closed。

**机制证据**：`test_controlled_prep_workflow.py`、`test_course_prep_agent.py`、`test_prep_intent_routing.py`、`test_oj_run_semantics.py`、`test_p1_7_judge0_sandbox_port.py` 等直接覆盖上述门控与降级语义。

## 5. 机制三：模型学科化——六维认知与垂类微调

> 问题：掌握度若只是一个概率，教师无法据此行动（P2）——0.7 的概率不回答"学生是概念混淆还是练习不足"。因此系统把学习者状态显式建模为**六维可解释向量**，并把模型本身的学科化作为独立工程问题处理。

### 5.1 RE-KT：六维认知状态

`cognitive_service.py` 的 `compute_cognitive_state` 从**服务端评分证据**计算六维（模型 `CognitiveState`）：

**（1）表现分 performance**——评分型证据的加权窗口均值：

```text
observed_performance = Σ(score_i × w_i) / Σ(w_i)
quiz_accuracy w=1.0；coding_execution w=1.5（代码执行权重高于选择题）
Σw ≥ MIN_EFFECTIVE_SCORED_WEIGHT=3.0 才产出（样本不足宁缺毋假）
```

**（2）置信度 confidence**——证据量的饱和函数而非计数：

```text
evidence_confidence = min(0.95, Σw / (Σw + 3))    # 饱和常数 3
观看时长达标时 +0.05 boost（仍以 0.95 封顶）
```

**（3）困惑度 confusion**——错误率与重复错误的结构化合成：

```text
wrong_rate   = |{score < 0.6}| / |judged|          （样本 ≥ 3）
repeat_factor = 重复出错题数 / 出错题总数
confusion = min(0.7 × wrong_rate + 0.3 × repeat_factor, 1.0)
```

区分"广泛性错误"与"卡在同一题"——后者才指向概念性误解。

**（4）提问深度 inquiry_depth**：最近窗口 `QuestionDepthRecord.depth_score` 均值（由 TeachingAgent 每次提问后写入）。

**（5）提示依赖 hint_dependency**：`hinted / total`（题库 hint_used 与代码 episode hint_used 合并观察，样本 ≥ 2）。

**（6）解释需求 explanation_need**——三维投影的加权合成：

```text
explanation_need = min(1, 0.5×confusion + 0.3×(1−performance) + 0.2×hint)
```

掌握分层阈值：`≥0.8 advanced / ≥0.6 proficient / ≥0.4 developing / else beginner`。

**时间衰减**（`cognitive_decay_service.py`）：

```text
decay_factor = 2^(−elapsed_days / half_life)
```

按知识半衰期投影（`COGNITIVE_HALF_LIFE_DAYS` 配置）；衰减是**读取侧投影**——存储行从不被改写（"Read-only projection: the stored row is never mutated"），`DECAY_MARK_THRESHOLD=0.99` 以下才在 `reason_codes` 追加 `evidence_decayed`。

**设计取舍**：六维对 BKT/DKT 类方法放弃预测精度换取可解释性——教师看到"confusion 0.72 + hint 0.5"可直接行动（重新讲解概念而非加练习题）。数据驱动估计器保留为接口位，hybrid 方案见《实验补充与验证计划》K1。

### 5.2 证据准入：只有服务端评分能写学习证据

`observed_performance` 的输入白名单在代码中显式声明：只有 server-scored quiz attempts 与 **server-owned finalizer**（`experiment_finalize_service` / `coding_episode_finalize_service`）写入的代码证据可进入；诊断输出或客户端提交分数**结构上无法**进入该路径（`_scored_observations` 注释即此契约）。

**Episode 聚合抗刷分**（`coding_challenge_service.py`）：一个 guided session 结束（45 分钟不活跃自动 close）只聚合为**一个** episode 证据——`evidence_id = "ev_" + uuid5(URL_NS, "coding_episode|{episode_id}|{node_id}")`，同一 episode 幂等（已存在直接返回原记录）；挑战替换上限 2 次（`replacement_count >= 2` 拒绝）；`best_score` 经 `_server_score` 归一化 `min(1, max(0, run.score))`。多次提交堆叠证据在结构上不可行。

### 5.3 提问反推：最小化投影

认知侧不直接读对话原文（数据最小化），而是消费结构化信号（`conversation_service.py` 的 `derive_question_inference_signals`）：按概念分组（无概念归 `course_level`），输出 `question_count / avg_inquiry_depth / depth_label_mode / inferred_weak / trace_ids`；薄弱判定阈值 `INFERENCE_WEAK_DEPTH_THRESHOLD=0.4`（平均提问深度低于 0.4 才标记，避免单次浅提问误判）。对话域独立持久化：`data_policy_version="conversation-domain/1"`，默认保留窗口 90 天（`retention_until`），读取/删除均按窗口过滤。

### 5.4 领域 SFT：学科垂类微调

针对通用模型在计算机学科口径上的漂移，对星火 X2.5-4B（4.11B dense，混合注意力 3×sliding-window-512 + 1×full，GQA 16Q/4KV）做 LoRA 领域微调（`backend/finetune/`）：

- **防污染方法论**：3127 训练 + 231 验证样本，其中**基准 10 问只进 eval 集不进训练集**——评测题不参与训练，杜绝"背答案"性虚高；学科知识点由知识库节点自动发现，与 RAG 语料同源。
- **架构适配的工程严谨性**：X2.5 将 q/k/v 融合为单一 `q_k_v_proj` 并带门控 `g_proj`，微调目标模块需按权重类型精确分发；投影名匹配不当将导致 LoRA 目标模块零命中，管线在装配阶段做类型分发校验。
- **实测结果**（4090 / 3 epochs / 588 steps / 26 分钟）：train_loss 0.2032；同分布验证困惑度 **10.98 → 1.057**（近十倍收敛）；基准 8 题通过基座与微调均为 4/4。收益集中于**同分布拟合与学科口径贴合**（术语、公式排版、学科语言风格），而非通用知识增量——因此系统将微调定位为"口径对齐"轨，与 RAG"知识供给"轨并行，共同构成学科化双轨。
- adapter 权重 140MB 已随 `70a631dc` 交付；QLoRA 4bit 降级路径保留，供低显存复现。

## 6. 机制四：Nexus Agent Harness 与可验证执行链

> 问题：科研任务需要数十轮工具调用、跨天恢复与真实代码执行（P4）；单轮"意图→动作→响应"式路由无法承载，且"实验结果"绝不能出自 LLM 之口。因此系统用独立运行时承载 **Agent Loop + Checkpoint + 一次性审批 + 受限执行 + 确定性判定** 的完整链条。

### 6.1 Agent Loop：Deep Agents 装配

开放科研任务无法用固定工作流穷举：任务结构未知、工具序列长达数十轮、中途需按观察结果重规划——固定流程在第三步就会丢失任务结构。因此 Nexus 采用 Agent Loop 把"规划—执行—观察—再规划"交给模型循环推进，`nexus/src/nexus/agent.py` 的 `build_agent()` 装配如下：

```python
create_deep_agent(
  model = build_llm()                       # DeepSeek OpenAI 兼容端点
  tools = _tools_for_mode(mode, execution_mode)
  system_prompt = SYSTEM_PROMPT + MODE_PROMPT_APPENDIX[mode]
  subagents = [researcher(只读)]             # Research 模式装配
  middleware = [ FilesystemMiddleware(tools=["read_file"]),
                SummarizationMiddleware,      # Context Compact
                TodoListMiddleware ]          # 计划（NX-H1）
  checkpointer = saver                        # Postgres / InMemory
)
```

从路由式到 Loop 的本质差异：模型每轮可"继续调用工具 / 观察 / 终结回答"，观察结果回灌上下文；`todos` 计划状态由真实 state update 投影为 SSE `plan` 事件（前端可见任务拆解），且 prompt 明确约束"todos 是模型的计划标记，不等于工具成功或实验 PASS 证据"。

### 6.2 工具面治理：显式排除 + 请求作用域注入

Agent 的自主性越强、工具面越宽，被提示注入利用后的破坏面越大——一个能直接写文件、执行命令的子代理是最大风险源。因此工具分配遵循**默认不给、按模式显式给**：

```python
NEXUS_EXCLUDED_TOOLS = {ls, write_file, edit_file, delete, glob, grep, execute, task}
```

默认只保留 `read_file`；文件写入能力被收敛为结构化 `write_artifact`（经 Backend 落对象存储，归属用户）。Research 模式装配只读 `researcher` 子代理，工具面仅 `{web_search, search_arxiv_papers, read_attachment, collect_paper_evidence, read_paper_more}`——**子代理无权审批、执行实验、写产物**。课程检索工具的 `course_id` 来自代理层注入的请求作用域（request_scope），**不信任模型传参**；调用旧 Backend 内部端点携带 `Bearer` 服务令牌 + `X-Nexus-User-Id`，失败码显式（`COURSE_ACCESS_DENIED / KNOWLEDGE_RETRIEVAL_UNAVAILABLE / COURSE_CONTEXT_MISSING`）。

### 6.3 Context Compact 与 Checkpoint

数十轮工具循环会把上下文推向 token 上限（超限即中断），跨天任务还要求中断后可续——前者需要压缩、后者需要检查点，且两者必须协同：摘要随 checkpoint 持久化，恢复时任务结构才不丢失。

**Compact**（DeepAgents 原生 `SummarizationMiddleware` + `StateBackend`）：token 超过阈值（配置 `summary_trigger_tokens`，默认 200000）触发，旧历史经同一 LLM 摘要并 offload 到 StateBackend（随 checkpoint 持久化），保留近期 `summary_keep_messages=20` 条——长任务的上下文不会无界膨胀，且摘要可随 checkpoint 一并恢复。

**Checkpoint**（`nexus/src/nexus/persistence.py`）：thread 命名空间化 `user-{uid}:nexus-session-{sid}`（session_id 白名单 `[A-Za-z0-9\-_]`、长度 ≤128），Postgres checkpointer 独立 schema `nexus_checkpoints`，与业务库分域。Nexus 自有 11 张表（threads/proposals/approvals/experiment_runs/session_prefs/operation_intents/execution_leases/document_jobs/research_tasks/research_evidence/compares）；`nexus_threads` 以 `updated_at` TTL（`NEXUS_RETENTION_DAYS`）到期调用 `PostgresSaver.delete_thread` 清理三表数据。恢复入口 `GET /api/v1/nexus/plan/{session_id}` 从 checkpoint 投影最近计划。checkpoint 只保留结构化状态，**不持久化完整 LLM trace/prompt**（数据最小化）。

### 6.4 一次性审批票据

复现执行前置人工批准（`nexus/src/nexus/approvals.py`）：

```text
approval = { approval_id ("apv_"+UUID), user_id, session_id, tool, preset_id,
             plan_hash, budget, status, job_id, expires_at,
             proposal_id, proposal_version, proposal_hash,
             frozen_steps, scope_hash, frozen_scope, frozen_license }
plan_hash = hash({preset_id, repo_url, repo_license, steps})   # 计划任何变化即失效
```

`run_reproduction` 无票据时**只创建 proposal/approval，不执行任何代码**（返回 `APPROVAL_REQUIRED`）；用户在审批卡批准后，`consume_approval` 以 CAS 原子核销：

```sql
UPDATE nexus_approvals SET status='consumed'
WHERE approval_id=%s AND status='approved' RETURNING ...
```

核销校验六项：票据存在、本人、同 session、状态 approved、未过期、`plan_hash` 一致（提案路径另验 version/hash 与执行锁定）。错误码显式：`APPROVAL_NOT_APPROVED / APPROVAL_EXPIRED / APPROVAL_FORBIDDEN / APPROVAL_SESSION_MISMATCH / APPROVAL_PLAN_CHANGED / APPROVAL_PROPOSAL_CHANGED`。已核销票据幂等返回原 `job_id`，不重复执行；审批服务端生成 ID，模型无法伪造票据。操作层另有 `nexus_operation_intents`（`intent_key` 主键）与 `nexus_execution_leases`（fencing 租约）支撑断点续跑的幂等。

### 6.5 Repro Worker：受限执行环境

`deploy/repro-worker/worker.py`（`WORKER_VERSION=0.3.0`）是"能不能跑"的物理边界：

- **资源限制双层**：容器层 `--cpus 1.0 --memory 2g --pids-limit 512`；进程层总超时 `TOTAL_TIMEOUT_S=900`、单步 `STEP_TIMEOUT_S`（代码默认 300s，生产部署 720s）、磁盘配额 `DISK_QUOTA_BYTES`（2GB）、并发 `MAX_CONCURRENT=1`（asyncio.Semaphore）。
- **环境白名单**：子进程环境只保留 `PATH/HOME/LANG/LC_ALL/TZ/TMPDIR/USER/LOGNAME/SHELL/TERM` 等——**Worker 自身凭据不进入子进程环境**，实验代码无法窃取上游密钥。
- **进程组回收**：每步 `create_subprocess_exec("bash","-lc",...)` 以 `start_new_session=True` 运行（POSIX），超时/取消时 `os.killpg(SIGKILL)` 整组回收，不留孤儿进程。
- **取消语义状态机**：`cancelling`（已请求未落地）→ killpg 落地；终态（succeeded/failed/rejected/cancelled）取消幂等返回原状态；取消晚到记 `cancel_late`，真实结果不被覆盖。
- **License 三源判定**：请求声明 + GitHub API（`_github_license_spdx`）+ clone 后本地扫描（根目录优先，无声明才递归）综合判断；GPL 一票否决；允许清单 `MIT/Apache-2.0/BSD-2/BSD-3/ISC/0BSD/Unlicense/CC0-1.0`；三源均不可识别即拒绝（`LICENSE_VIOLATION`，fail-closed）。
- **日志与产物最小化**：`_redact_secrets` 正则族遮蔽 ANSI/Bearer/Cookie/API-key/OpenAI/GitHub/HF/AWS/JWT/URL-userinfo；每步日志环形缓冲 ≤8000 字符、对外 `log_tail` ≤4000；产物仅回传白名单 glob（`*.log/*.txt/*.json/*.csv/*.md`，单个 ≤1MB）的**清单**（path+size），内容不回传。

### 6.6 确定性判定：结果不经 LLM 之口

职责切分：**LLM 负责规划与解释，Worker 负责真实执行，判定由 Runtime 报告链完成**。Worker 只回传状态/步骤结果/日志尾部/产物清单；指标提取与阈值比较在 Runtime 报告链执行，verdict 经 `POST /jobs/{job_id}/metric` 回写 `PASS / FAIL / INCOMPLETE`——**PASS/FAIL 是程序对数值与容差的比较结果，LLM 全程不参与判定**。

**真实执行实证（nanoGPT 预设）**：

```text
Repository: karpathy/nanoGPT（MIT）
Preset:     人工核验预设（REPRO_PRESETS 白名单）
Compute:    CPU · 总超时 900s · 并发 1
执行:       5/5 steps succeeded（真实 Worker 执行）
预期:       val_loss = 1.88 ± 0.06
实际:       val_loss = 1.8857
判定:       PASS（确定性数值比较）
产物:       report.md / report.json 落库为 Artifact（M4 验收 2026-09-05）
```

未命中预设时返回 `UNKNOWN_PRESET` 并列出 `known_presets`——系统**不编造命令**，未知仓库的自动复现属于后续建设。三问分离由此完整："该不该跑"（License+审批）/"能不能跑"（Worker 资源边界）/"跑成没有"（确定性判定）。

**设计取舍（为何不复用 Judge0）**：Judge0 面向单题级编译运行（10 语言白名单、秒级 CPU 限制），而论文仓库是仓库级、分钟到小时级、依赖网络与文件系统的高风险执行场景——两者安全模型不同，故独立 Worker 施加不同资源/环境/许可边界。

## 7. 机制五：Artifact 与多模态输出

> 问题：科研与教学产物若只是聊天文本，无法沉淀为可管理资产。因此产物统一走对象存储与归属管理。

`write_artifact`（`nexus/src/nexus/tools/artifact.py`）：类型限 `markdown / latex`，标题 ≤120 字符，内容 ≤512KB；经 Backend 内部端点写入对象存储并绑定 `user_id` 归属（`X-Nexus-User-Id`），返回 `artifact_id + download_path + size_bytes`；失败码 `ARTIFACT_UNAVAILABLE`。二进制产物（如 `.docx`）经 base64 通道由 `write_binary_artifact_via_backend` 写入。LaTeX 产物以 `.tex` 源文件交付，在线编译与 PDF 预览列入后续路线。跨用户访问经 owner 校验（404 语义）。

**多模态教学侧**：讲稿 TTS 合成与数字人视频生成构成"文字讲稿 → 可听可视课件"管线（P0 能力），媒体资产经 `object_key` 引用、发布不可变、修改即新版本（旧版本标 stale）。

## 8. 权限与安全底座

| 维度 | 机制 | 失败语义 |
|---|---|---|
| 课程访问 | Course Access v1：`CourseMembership + CourseCapability + PlatformPermissionAssignment` 解析；`User.role` 仅遗留迁移输入 | 无权限 403；资源不存在 404（不泄漏存在性）；服务令牌无效 401 |
| 跨用户隔离 | Artifact/Job owner 校验；Nexus thread 命名空间按用户隔离 | 跨用户 404/`RUN_SESSION_MISMATCH` |
| 工具调用 | per-tool policy check + 治理审计；请求作用域注入 course_id | `TOOL_BLOCKED_BY_HARDNESS`；禁用工具跳过并写审计 |
| 外部检索 | SearXNG（12s 超时）→ DuckDuckGo 降级；arXiv 直连 Atom API → SearXNG `site:arxiv.org` → DDG（限速 3s 间隔、缓存 TTL 86400s/200 条） | `WEB_SEARCH_UNAVAILABLE / ARXIV_UNAVAILABLE`，失败不伪造 |
| 代码执行 | Judge0（教学）/ Repro Worker（科研）双沙箱；未知代码不进主进程 | `SANDBOX_UNAVAILABLE / LICENSE_VIOLATION` |
| 数据最小化 | checkpoint 只存结构化状态；对话域 90 天窗口；审计与学习证据严格分域 | 读取按窗口过滤 |

fail-closed 家族的共同语义：**宁可明确报不可用，不给假结果**。

### 9.3 机制必要性论证

| 移除机制 | 失效后果（推断自现有测试覆盖的语义） | 对应可执行实验 |

| Citation 闭包 | 检索块失去 `evidence_ids/citation_ids` 声明，模型可引用不存在的出处且不可检测 | S1 引用合法率（开/关对比） |

| Episode 聚合 | 多次提交堆叠证据，掌握度可被刷分污染 | 现有单测覆盖幂等核销 |
| 一次性审批 CAS | 同一票据可重放执行，实验执行失去人工监督点 | X1 注入对抗（审批绕过） |
| Worker 环境白名单 | 实验代码可读取 Worker 凭据（API key 出域） | X1 注入对抗（凭据窃取） |
| 确定性判定 | PASS/FAIL 退化为 LLM 断言，复现结论不可信 | R2 确定性 vs LLM 判定对照 |

## 附录 A　相关研究与方法定位

### A.1 系统组合的定位

本系统的贡献属于**系统工程与机制组合**：citation 闭包、双门控、六维认知、确定性判定均为公开领域思想的组合与工程化，非基础方法原创。此定位刻意明确——组合的原创性体现在"把不可信任的生成改造为可验证的教学/科研产物"这一完整链条上，而非任何单项算法。

### A.2 可信 RAG

系统把来源闭包形式化为：`C_output ⊆ R(q, u, c, v)`——回答引用集合必须落在问题 q、用户 u、课程 c、版本 v 共同决定的许可证据集内。对照 ALCE（引用忠实但未做版本冻结）、RAGAS/ARES（离线评测框架而非运行时约束），本系统的差异点在**运行时闭包 + 发布快照冻结**的组合。后续评估方向：引用蕴含（cite-worthiness）与引用完备性（completeness）分级。

### A.3 Agent 与安全

Agent Loop 对照 ReAct（单轮思维链）与 AgentBench（评测基准），本系统采用生产级 Harness（Deep Agents）并叠加权限收口：工具显式排除、请求作用域注入、一次性审批。安全评估对照 Agent-SafetyBench/InjecAgent 的注入鲁棒性子集（见《实验补充与验证计划》X1）。

### A.4 知识追踪

RE-KT 的学术定位是"证据驱动、面向教学动作的学习者状态模型"：以可解释六维换取教师可行动性，区别于 BKT/DKT/AKT/simpleKT 的预测精度取向。评估路线：以 pyKT 为底座、统一预处理与 student-level split，报告 AUC/Brier/ECE 并对照校准；教师效用（重讲/提示触发的接受率）作为第二指标（K1/K2）。

### A.5 复现语义分级

在此基础上，系统把"能否复现"进一步拆解为四级语义：`executed` → `metric-reproduced` → `result-reproduced` → `conclusion-reproduced`。当前 nanoGPT 实验具备前两级（真实执行 + `val_loss=1.8857` 达标）；后续以多 seed 保存并报告 mean/σ/95%CI，使"跑过一次"提升为"同一快照重复运行统计一致"。
