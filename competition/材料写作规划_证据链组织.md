## 一、为什么五份材料要组成"一套证据链"

评委拿到材料包的阅读顺序，对应五个递进的问题：

| 材料 | 核心回答的问题 | 面向谁 | 目标长度 |
|---|---|---|---|
| **README.md** | 我拿到代码后 3 分钟能看懂项目是什么、怎么跑吗？ | 技术评委/复核人员 | 1–3 页 |
| **技术报告.md** | 这个系统为什么值得"评"？怎么设计、怎么实现、为什么这么选？ | 技术专家 | 12–20 页（建议 15 左右） |
| **复现说明 REPRODUCIBILITY.md** | 别人能不能把系统/实验重新跑起来、验证你所说的真能跑？ | 技术复核 | 3–8 页（建议 5–6） |
| **测试报告 TEST_REPORT.md** | 你们怎么证明它稳定，不是"刚好能演示一次"？ | 技术评委 | 5–10 页（建议 6–8） |
| **效果验证报告**（材料 06） | 这个系统**对真实用户到底有没有用**、输出是否可信且可执行可验证？ | 评委 | 6–10 页（建议 8） |

**避免重复的组织逻辑**（判断某段是否放错位置的标尺）：

```text
README       "是什么、怎么跑"        —— 导航，不展开原理
技术报告      "为什么这样设计、怎么实现" —— 原理与取舍，不写操作步骤
复现说明      "怎么重新跑出来"        —— 步骤与预期输出，不写设计动机
测试报告      "怎么证明它稳定"        —— 断言、命令、计数，不写用户感受
效果验证      "真实用户和真实实验表现"  —— 反馈、实测数值、判定结果
```

**同一份证据只在"职责所在的那一份"写全**，其余各份只做一句话索引，不复制粘贴。例如 nanoGPT 复现：测试报告讲"确定性判定链路测过 20 例、断言矩阵"，效果验证讲"真实线上跑出 val_loss 1.8857 PASS"，复现说明讲"按第 X 节步骤可重跑得到该数值"——各取一角，互不重复又互相印证。

**共同证据锚点**（所有材料统一引用，避免口径漂移）：

| 证据 | 权威来源位置 |
|---|---|
| 基线提交 SHA | HEAD `44728392`；但 **每份报告引用的数字须从最终打包 commit 重跑**，不照抄此 SHA |

| nanoGPT 复现实证 | `docs/phase1/验收记录/M4_验收_2026-09-05.md`（val_loss 1.8857 ∈ 1.88±0.06，PASS，LLM 零参与，越权 404 双向实证，report.md/`.json` 落库） |

## 二、现状盘点：哪些是真证据、哪些要新采、哪些阻塞

| 材料 | 已有/可整理（真证据） | 待补充 | 阻塞/依赖 |
|---|---|---|---|
| README | 根 `README.md` 已较完善（能力矩阵、架构、快速开始、部署） | 精简为 1–3 页导航版；新增跳过细节的"仓库入口"式开头 | 无 |
| 技术报告 | v2.0 创新主线版已存在（Citation 闭包、双源证据、双门控、Nexus 可信复现等 8 点带代码索引） | 与新推荐 14 章结构做一次**融合**：补总体架构图、教学/科研两条产品链全貌、设计取舍（why）段落 | 无；主要工作是对齐+补图 |
| 复现说明 | M4/nanoGPT 完整链、验收记录的启动步骤、POSTGRES/Worker 配置 | 独立成 `REPRODUCIBILITY.md`：系统级 + nanoGPT 复现案例 + 明确"不能复现清单" | 无 |
| 测试报告 | 07 下已有"测试报告说明"（计数表）、P2 §6 测试覆盖矩阵、验收记录 | 独立成 `TEST_REPORT.md`：断言矩阵 + 证据（命令/commit/日期/环境/输出）+ 总表；**数字须复跑最终 commit** | 需在新 commit 上重跑测试 |
| 效果验证 | 10 用例 9/9、nanoGPT 实证、结构化测试表已回填 | **关键在于用户试用**：≥2 名真实用户（U1/U2）、3 分钟视频、截图；"nanoGPT 科研可执行验证"页 | **用户反馈 + 视频 + 截图 = 当前最大外采项** |
| 07 其他材料 | 测试脚本、nanoGPT 执行记录、安全/伦理、已有截图素材 | 高清架构图 PDF、真实用户原始反馈表、精选 6–10 张截图 | 架构图需从代码/文档绘制 |

### 关键结论（供排优先级）

1. **效果验证报告是最难"临时补"的**——真实用户、视频、截图无法靠写补出来，应最先启动（用户 A 的联系与试用排第一）。
2. **README + 复现说明**几乎全是已有事实整理，成本最低，可快速完成。
3. **技术报告**以 v2.0 为基础做"补全 vs 精简"的结构融合，中等成本。
4. **测试报告**的唯一成本点是"在最终 commit 上复跑一遍测试"，须排在提交前。

## 三、执行顺序与风险（建议优先级）

### 总顺序

```
第一批（立即，几乎不依赖外部）：
  ① README 精简为导航版
  ② REPRODUCIBILITY.md 成文
第二批（与用户试用并行）：
  ③ 技术报告 v2.0 → 补齐架构图 + 设计取舍 + 产品链全貌（15 页）
  ④ 效果验证报告骨干（先搭"教学/科研两条线 + nanoGPT 页"骨架，等 U1/U2 数据）
第三批（提交前必经）：
  ⑤ 在最终 commit 上复跑全部测试 → TEST_REPORT.md 填真实数字
  ⑥ 03 Demo URL + 6–8 张截图 + 3 分钟视频
  ⑦ 07 组装（架构图/反馈原表/精选截图）+ preflight 复跑清零
```

### 依赖矩阵

| 产出物 | 前置 | 无前置则风险 |
|---|---|---|
| 效果验证 U1/U2 数据 + 视频 + 截图 | **需真实用户与实际系统演示** | 无法完成→用户认可度 10 分失去主要证据 |
| TEST_REPORT 数字 | 最终打包 commit | 用旧数字→被复核发现口径不一致，诚信受损 |
| 架构图 | 需确认最终架构（含 Nexus/Sandbox 现状） | 画错→误导专家 |
| 复现说明 | 线上/本地环境可跑 | 无法验证→写成"看起来能跑" |

### 诚实边界与数字纪律（每份材料都必须遵守）

- 未完成项不得写成已实现：完整 Paper Research、A/B Clean Verification、通用任意附件、GPU 多云调度、nanoGPT 之外的任意论文复现，**全部标注为"后续/不支持"，且明确写出当前边界**（见 RE 文档"不能复现清单"）。
- **测试数字绝不照抄旧记录**：必须标注 `Commit / 命令 / 日期 / 环境 / 输出`，且数字在最终 commit 重跑得到。
- 用户反馈不得编造：试用对象须真实（CS 专业教师/学生），记录含身份标注，如"共完成 6 个结构化任务，6 个成功返回，5 个无需人工修正，1 个需补充提示"这类可核实表述；**绝不写"准确率 97.3%"这类未做的正式标注评测**。
- 报告里可写失败与异常（无课程权限时拒绝 Course RAG、Worker 不可用时明确错误、当前 Paper Research 未支持全文证据综合）——这反而增强可信度，效果验证 §8 专设"异常与失败情况"。

## 四、分材料写作蓝图

### 4.1 README（根目录，1–3 页，导航角色）

- **目标**：技术评委解压后第一眼看懂"是什么、怎么跑、往哪儿看"。
- **结构**：
  1. 项目一句话定位（CodeNexus：面向计算机学科教学与科研的智能体平台）
  2. 能力速览三块：**Teaching Agent**（课程学习/练习/Judge0/认知）· **Nexus AI**（Course/CS RAG、Web、Artifact）· **Nexus Research**（arXiv 检索、Quick Reproduction）
  3. `Repository Structure`（backend/frontend/nexus/deploy/...）
  4. 运行结构简图（Browser→Backend→Nexus Runtime→Tools/RAG/Repro Worker）
  5. Quick Start：仅给最短启动路径 + 3 行跳转（完整部署→`DEPLOYMENT.md`、复现→`REPRODUCIBILITY.md`、测试→`TEST_REPORT.md`）
- **不写**：40 条安装命令、设计取舍、测试明细。
- **现状动作**：现有根 README 信息过载且偏正式项目介绍，需裁剪进上面骨架；能力矩阵可保留但移到底部或拆入技术报告。

### 4.2 技术报告（`competition/05-作品代码/技术报告.md`，建议 ~15 页）

- **定位**："这个系统为什么值得评"。核心是设计动机与取舍，不是操作手册。
- **结构**：在现有 v2.0 创新主线基础上**融合**新推荐 14 章，建议总结构：

  ```text
  1. 项目背景与问题定义（三条刚性约束 + 四个常见缺陷）
  2. 产品定位（助教/助学/助研 + Nexus 全局入口）
  3. 总体架构（★★★ 放最终版架构图：Frontend→Backend→[Auth/RBAC|Course|CS Knowledge|Teaching Agent]→Nexus Gateway→Nexus Runtime(Deep Agents)→[RAG|Web/arXiv|Artifact]→Nexus Research→Repro Worker）
  4. 关键技术创新（保留 §2 的 8 点，作为报告"含金量"主体）
     —— Citation 闭包与失败关闭检索
     —— 双源证据分层与六维认知
     —— 双门控生成治理
     —— 对话最小化投影
     —— 分级失败语义工具治理
     —— 不可变版本快照
     —— Nexus 可信复现执行（三问分离）
     —— 微调评测方法学
  5. Teaching Agent（25 节点工作流、Judge0、认知）
  6. Nexus AI（Course/CS RAG、Web、Artifact）
  7. Nexus Research（arXiv 检索、Quick Reproduction 审批门）
  8. 知识与 RAG 架构
  9. Agent Harness（Tool loop / Compact / checkpoint 恢复）
  10. NexusLab / Repro Worker
  11. 安全与权限（Course Access v1、fail-closed）
  12. Artifact 与可追溯性
  13. 真实运行结果（nanoGPT 实证 + 10 用例 + 测试基线）
  14. 当前边界与后续迭代（如实区分）
  ```

- **必写"为什么这么选"（设计取舍）**，专家很看重，示例：
  - *Deep Agents*：原 ResearchAgent 为单 Action 路由式，难支撑持续 Tool Loop / Context Compact / 长任务恢复 → Nexus Runtime 独立采用 Deep Agents + LangGraph，与旧 Backend LangGraph 进程级隔离、依赖树互不牵连。
  - *Repro Worker*：不直接复用 Judge0——学生题目级代码执行与未知科研仓库运行**安全模型不同**（前者沙箱内、后者需 License/预算/资源审计），故独立受限 Worker。
  - *六维认知而非单一 BKT 掌握概率*：可解释性优先——六维对应教师真实关心的六个判断维度，规则的 rule_baseline 为当前实现，BKT/DKT 保留接口待升级（升级前提是保持可审计）。
- **现状动作**：v2.0 已有 8 点创新主体与代码索引；需①补 §3 总体架构图，②把产品链全貌（Teaching/Nexus AI/Nexus Research）从散落各节归并成连续章节，③新增"设计取舍"表述，④控制到 ~15 页、压缩只列概览的常规实现。

### 4.3 复现说明 REPRODUCIBILITY.md（新建，建议 5–6 页）

- **定位**："我拿到你代码以后，怎么证明你说的东西确实能跑"。分两层。
- **A. 整体系统复现**：Prerequisites（Linux/Docker/Python 3.12/Node/PostgreSQL）→ 分步启动 Backend / Nexus Runtime / Frontend / SearXNG / Repro Worker，每步给出：环境、配置、启动命令、健康检查、预期结果（如 `curl http://localhost:8300/health` → `{"status":"ok","persistence":"postgres"}`）。命令与预期结果取自既有部署/验收记录，不凭空写。
- **B. nanoGPT 复现案例（亮点页）**：

  ```text
  Preset: nanogpt ｜ 仓库: karpathy/nanoGPT ｜ License: MIT
  Compute: CPU ｜ Timeout: 900s
  预期：val_loss 目标 1.88，容差 ±0.06
  实测：1.8857 ｜ 判定：PASS（程序确定性比较，LLM 零参与）
  证据：M4 验收记录（job c3e71851e513，5 步 succeeded，report.md/.json 落库）
  ```

- **C. "不能复现清单"（写清楚边界，是加分项不是减分项）**：

  ```text
  目前不包含：
  - 任意论文自动复现（仅 preset 白名单，未命中返回 no_preset）
  - 自动 Paper→Repo 匹配
  - A/B Clean Verification（reproducible=true 不由此给出）
  - GPU 多云调度 / repo2docker 构建链（fail-closed 未交付）
  - LaTeX 编译证明（TOOLCHAIN_MISSING）
  ```

### 4.4 测试报告 TEST_REPORT.md（新建，建议 6–8 页，07 目录或独立）

- **定位**：回答"软件质量怎么样"，不是"用户喜不喜欢"。与效果验证完全分开。
- **结构**：

  ```text
  1. 测试范围与方法（功能/接口/权限/Agent Harness/Repro Worker/安全/异常/部署）
  2. 测试证据格式（命令 + commit + 日期 + 环境 + 输出）——务必统一
  3. 总表（类别×数量：Nexus Runtime / Frontend Contracts / Repro Worker / 后端 nexus 域 / 学科知识库 + 全校 permissions，通过/失败）
  4. Nexus 域：Multi-tool / Tool 超时 / Context overflow / Runtime restart-resume / Cancel / Malformed Tool / Worker timeout
  5. 权限与安全：无权限课程 403 / service token 错 401 / 跨用户 Artifact 404 / job owner 隔离
  6. Reproduction：nanoGPT 5 步链 / 900s 超时 / License fail-closed / 确定性指标判定
  7. 已知失败与边界（graphrag 模块、BGE 权重缺失引起的 6 个可选失败；诚实说明）
  ```

- **红线**：**数字从最终 commit 重新跑一次，不照抄旧记录**；每个断言注明来源文件（测试文件名）。现有 07"测试报告说明"可作为初稿底料，但**必须以复跑结果覆盖**。

### 4.5 效果验证报告（材料 06，建议 ~8 页）——最值得认真做

- **定位**：证明两件事——①用户觉得有没有用；②系统输出可信、可执行、可验证。**不是"测试报告换个名字"**。
- **拆"教学应用验证 + Nexus 科研验证"两条线**，推荐目录：

  ```text
  0. 验证对象与方法（首屏：≥2 真实用户身份标注；验证对象=Teaching/Neuxs AI/Neuxus Research；验证方式=试用/任务记录/系统日志/可执行实验/定量指标/结构化反馈）
  1. 教学场景验证：教师 A"根据课程资料回答二分查找边界错误并给出处"、学生 B"解释 Attention 复杂度+课程资料+通用知识"
     —— 记录：是否完成/是否正确知识源/是否有课程引用/是否明显错误/完成时间/用户评分
  2. Nexus AI 多源任务验证（Course/CS RAG、Web、Artifact 生成）
  3. Nexus Research 可执行验证 ★核心页：nanoGPT 复现流程（Nexus Research→Plan→Worker→真实 CPU 训练→val_loss 1.8857→程序确定性比较→PASS）+ 3 张截图（调用复现/Worker 执行/report.md.json）
     ★关键句："实验结果来自真实 Worker 执行，PASS/FAIL 由程序依据预设目标值与容差计算，大模型不参与最终判定。"
  4. 结构化测试记录（已回填 10 用例 9/9，C3 待补 Judge0 截图）
  5. 用户结构化反馈（U1/U2 汇总；原表放 07）
  6. 异常与失败情况（无权限拒 Course RAG / Worker 不可用明确错误 / Paper Research 未支持全文证据综合）
  7. 结论
  8. 附录：截图、日志、视频链接
  ```

- **诚实边界**：真实反馈或结构化测试记录二选一满足"≥2 名真实用户"；表达用可核实口径（"6/6 成功、5 个无需修正"），**不用"准确率 97.3%"这类未做的正式评测**。

### 4.6 其他辅助材料（07，最多 4–6 项，不塞垃圾）

1. 测试脚本（`scripts/`、`tests/` 入口）
2. **高清架构图 PDF**（与技术报告 §3 同源）
