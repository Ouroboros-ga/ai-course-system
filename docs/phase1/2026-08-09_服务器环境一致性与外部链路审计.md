# 服务器环境一致性与外部链路审计

**日期：** 2026-08-09

**原因：** 将 Windows 本地 Demo 已完成能力迁移到 Ubuntu 22.04 服务器，并核实文件上传、文件解析、RAG、Judge0 与外部 Provider 的真实运行状态。

**证据：** 实际服务器命令、已注册路由与配置、`deploy/` Compose、生产 bootstrap、Provider 选择逻辑及合成材料冒烟。本文不以历史规划文档作为“已完成”证据。

## 结论

- Ubuntu 上未发现 LanceDB/PyArrow 二进制不兼容。LanceDB 0.34 + PyArrow 25 已在隔离 Linux venv 完成建表、写入和向量查询冒烟；索引仍必须在服务器本地构建并以 manifest/hash 验证，不能复制 Windows 索引目录。
- 上传失败的直接原因不是文件内容，而是 HTTP 非安全上下文没有 `crypto.randomUUID()`。前端已增加仅用于 UI key 的兼容 ID；后端文件上限为 100 MiB，Nginx `/api/` 请求体上限由 60 MiB 提升为 110 MiB，为 multipart 边界和角色字段保留空间。
- 文件解析已具备真实链路：LibreOffice/Poppler 已安装，PaddleOCR 2.7.3 CPU 容器已通过合成中文图片和 PDF 冒烟。Provider 不可用时返回结构化失败，不生成 Fake OCR/解析文本。
- GraphRAG 3.1.1 已放在独立 CPU-only venv，使用外部 completion LLM 和本地 BGE-small-zh-v1.5 embedding。GraphRAG 构图会产生外部 LLM 费用；LanceDB 与本地 BGE 本身不调用付费 API。
- 服务器只有 7.1 GiB 内存且无 swap。OCR 固定为 1 worker、3 GiB/2 CPU；Judge0 设定总上限约 2.7 GiB。不得并发执行 OCR 压测、GraphRAG 构图与多路 Judge0 压测。

## 找到的本地/Ubuntu 差异

1. Windows 文件系统不区分路径大小写，`Fileconfigmodal` 在 Windows 构建未暴露问题，Ubuntu 上无法解析；已改为真实目录名 `FileConfigModal`。
2. 原 BGE 相对路径指向本地研究目录，服务器不存在该目录；模型现在部署到 `backend/models/bge-small-zh-v1.5`，运行配置使用 `./models/bge-small-zh-v1.5`。
3. 后端目录包含运行时数据目录时，Setuptools 自动包发现会把它们误判成顶层包；`pyproject.toml` 已明确只发现 `app*`/`scripts*`。GraphRAG Worker 进一步采用最小依赖安装，避免安装 Docling/Torch/CUDA 大依赖。
4. PaddleOCR 2.7 不接受 Pillow Image，且单图返回值多一层 page list；Provider 已在边界内转换为 NumPy 并兼容两种结构，同时把 bbox 归一化。
5. GraphRAG 人工冒烟在主进程设置的 token/USD 上限原先不会自动进入隔离 Worker；现已显式传递四个预算环境项。
6. Linux venv 的 `bin/python` 通常是到基础解释器的符号链接；原代码调用 `Path.resolve()` 后绕过 venv，导致 Worker 找不到已安装的 `sqlmodel`。现只做绝对路径转换而不解析最终 symlink，并增加 Linux 回归测试。

## GraphRAG 与费用边界

- 实体/关系抽取和描述合并调用已配置的外部 completion LLM；配置为 `local_bge` 时，业务向量索引在本地计算。
- `GRAPHRAG_MAX_ESTIMATED_COST_USD` 只按输入 token 和配置单价做**预检估算**，不是供应商账单硬额度，也不覆盖输出 token、重试、供应商计费差异。要获得硬上限，仍须在供应商侧设置专用 Key/项目额度。
- 当前服务器闸门为最多 25,000 输入 token、US$0.70 输入估算、30 分钟。人工真实冒烟还要求显式 `--confirm-billable`，不会进入自动化测试。
- 构图失败不得替换 active bundle；成功产物仍需通过输入 hash、输出完整性、Evidence 闭包和教师审核/发布流程。
