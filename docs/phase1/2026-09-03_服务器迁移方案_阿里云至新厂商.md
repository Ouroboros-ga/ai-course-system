## 二、新机配置建议

### 2.1 推荐规格

| 项       | 推荐值                    | 理由                                                                                                                               |
| ------- | ---------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| **CPU** | **8 核**                | 当前 4 核已紧：Judge0 编译 + PaddleOCR CPU 推理 + 双 uvicorn worker + Nexus + Repro Worker 并发时互相排队。8 核留出演示流畅度余量                             |
| **内存**  | **16G**                | 现有容器 limit 合计 7GiB（postgres 1.5 + paddleocr 3 + repro 2 + searxng 0.5），再加 backend/nexus 运行占用与 Judge0 启动（需 2-4G），8G 必然超卖。16G 一步到位 |
| **系统盘** | **100G SSD**           | 干净部署后约 55G（镜像 27G + /opt 20G + PG + 备份），100G 留增长空间；与旧机同容量，rsync 命令无需调整                                                           |
| **带宽**  | 固定 ≥5Mbps，或按流量计费       | 迁移期间建议临时提升带宽或按流量付费跑一次（约 33G 传输，按量费用约几十元）                                                                                         |
| **地域**  | 中国大陆（尽量靠近演示评委所在地域）     | 挑战杯演示低延迟                                                                                                                         |
| **系统**  | Ubuntu 22.04/24.04 LTS | 与旧机一致，venvs/systemd 单元直接兼容                                                                                                       |

**可选优化**：若厂商支持，系统盘 50G + **数据盘 100G 挂载 /opt**。好处是未来再迁移只迁数据盘、系统可随时重装。若求简单，单 100G 盘即可。

**预算紧张降级**：4C8G 可维持现状（Judge0 与 Repro Worker 错峰启用），但演示高峰有排队/OOM 风险，不推荐。

### 2.2 带宽与传输量预估

- 预同步总量约 33G：/opt 20G + 自建镜像压缩后约 8G + PG dump 0.8G + 备份 4G

- 跨厂商公网有效 10-50MB/s 时全程 15 分钟\~1 小时；若固定 5Mbps（0.6MB/s）需约 15 小时 → **务必确认带宽计费模式，迁移窗口选按流量付费**

## 三、迁移方案（rsync 预同步 + 短停机割接）

核心思路：**rsync 幂等预同步（不停机）→ 新机演练验证 → 30-60 分钟停机窗口终态割接 → 旧机冻结保留作回退**。

### Phase A：新机初始化（半天）

1. 下单 8C16G/100G，系统 Ubuntu 24.04 LTS。
2. 基础组件：Docker Engine + compose 插件（**配置国内 registry mirror**，已踩过坑：Docker Hub 直拉超时）、git、uv、Node 22（与旧机 /opt/node-v22.23.2 同版本）。
3. 安全组：仅放行 80/443；SSH 22 限源 IP 白名单。
4. 复刻目录结构：`/opt/smartcarb`、`/opt/smartcarb-backups`、`/var/lib/smartcarb-postgres`（属主与旧机一致）。

### Phase B：预同步与演练（不停机，旧机照常服务）

1. **文件预同步**（可反复执行，增量续传）：

   ```bash
   rsync -avz --partial root@47.99.97.154:/opt/smartcarb/ /opt/smartcarb/
   rsync -avz --partial root@47.99.97.154:/opt/smartcarb-backups/ /opt/smartcarb-backups/
   rsync -avz --partial root@47.99.97.154:/root/smartcarb-backups/ /root/smartcarb-backups/   # 可选归档
   ```

   - venvs 原样拷贝（同路径 `/opt/smartcarb/shared/venvs` + 同 Python 3.12 + 同 OS，无需重建）。

   - `.env` 含密钥，仅走 SSH 加密通道，不打印、不入日志、不入文档。
2. **systemd 单元**：拷贝 `/etc/systemd/system/` 下 `smartcarb-*.service`、`smartcarb-*.timer`、`nexus-runtime.service` → 新机 `systemctl daemon-reload`（先不 enable）。
3. **镜像迁移**（分两类）：

   - **公共镜像直接重拉**（省 17G 传输）：postgres:16.14-alpine、searxng、redis、python:3.12-slim、judge0/judge0:1.13.1。

   - **自建镜像 save/load**：paddleocr(2.58G)、repro-worker(9.46G)：

     ```bash
     ssh root@47.99.97.154 'docker save smartcarb/paddleocr:2.7.3-cpu repro-worker:latest | zstd' \
       | ssh 新机 'zstd -d | docker load'
     ```
4. **PG 演练恢复**：取旧机 `/opt/smartcarb-backups/postgres` 最新 dump（每日 timer 已产出），新机起 postgres 容器 → `pg_restore` → 校验 162 张表行数与旧机一致。
5. **演练启动**（新机临时监听非 80 端口）：依序 postgres → backend → paddleocr → searxng → nexus → repro-worker，health check 全绿后跑一遍只读冒烟（登录、课程浏览、Nexus 一次 SSE）。
6. **前端 API 地址核查**：前端经 `VITE_API_BASE_URL` 构建（硬约束），构建产物中是否烘焙了旧 IP。若指向 `http://47.99.97.154`，新机前端需以新 IP 重新构建部署；若用相对路径则只改反代。

### Phase C：割接（停机 30-60 分钟）

按序执行，每步有验证点：

| 步骤 | 操作                                                                                                      | 验证                                |
| -- | ------------------------------------------------------------------------------------------------------- | --------------------------------- |
| C1 | 旧机停写入：`systemctl stop smartcarb-backend nexus-runtime`；`docker stop repro-worker`（postgres 保留运行用于 dump） | 无新请求进入                            |
| C2 | 旧机终态 dump：`docker exec smartcarb-postgres pg_dump -Fc ... > /opt/smartcarb-backups/postgres/final.dump` | dump 文件生成、非空                      |
| C3 | 终态 rsync 增量（差异极小，分钟级）+ 传输 final.dump                                                                    | rsync 无异常退出                       |
| C4 | 新机恢复：停演练库 → 重建库 → `pg_restore final.dump` → `alembic current` 校验（应等于 head，**不跑 upgrade** 除非 mismatch）   | 输出版本号与旧机一致                        |
| C5 | 新机依序启动全部服务（含 judge0）                                                                                    | `curl http://127.0.0.1/health` 全绿 |
| C6 | 完整演示脚本过一遍：登录 → 课程浏览 → TeachingAgent 问答 → 代码挑战（Judge0 真实执行）→ Nexus SSE 一次                                | 关键用例通过，截图归档                       |
| C7 | 切换入口：对外公布新 IP（无域名，无需 DNS；更新演示材料/README 中所有旧 IP 引用）                                                      | 全仓库 grep 47.99.97.154 清零          |
| C8 | 旧机服务保持停止、数据冻结保留                                                                                         | —                                 |

### Phase D：回退方案（保留至验证通过）

- 新机故障：停新机服务 → 旧机 `systemctl start smartcarb-backend nexus-runtime` + docker start 全部容器 → 入口指回旧 IP。

- 旧机数据以 C2 的 final.dump 为冻结基线，割接后新机若产生演示期写入，回退时以新机 dump 反向补救（演示场景写入极少，风险可控）。

- **旧机退租建议在割接后 ≥3 天、且至少完整演示彩排一次之后**。

### Phase E：收尾

1. 文档同步：README、AGENTS.md 部署地址、验收手册、比赛材料中 IP 全部更新（§7.1 同步纪律）。
2. 新机重建每日备份 timer，确认 `/opt/smartcarb-backups/postgres` 有产出。
3. 旧机最后一档 dump 留档 → 阿里云退租。

## 四、风险与对策

| 风险               | 对策                                                                 |
| ---------------- | ------------------------------------------------------------------ |
| 跨厂商公网带宽不足，预同步超时  | 按流量计费临时提带宽；zstd 压缩；rsync `--partial` 断点续传，可分目录分批跑                  |
| venvs 拷贝后不可用     | 路径/Python/OS 三同基本可用；真坏则 `uv sync` 重建（旧机 venvs 可重生成，非单点数据）          |
| PG 恢复后 schema 漂移 | 以 `alembic current` 对齐验证；pg\_restore 用 `--clean --if-exists` 保证可重入 |
| 国内拉公共镜像慢         | 新机 daemon.json 配 registry mirror（历史踩坑项）                            |
| 密钥泄露             | .env 仅 SSH 通道传输；迁移期间不 cat、不截图含密钥文件；完成后续查日志无密钥残留                    |
| 演示材料 IP 失效       | 割接 checklist C7 全仓 grep 更新；对外材料提交前再跑一次 preflight                   |
| 割接窗口超时           | rsync 终态增量已预演过，瓶颈只剩 PG dump/restore（1.4G 库 < 10 分钟）；预留 2 倍缓冲       |

***

## 五、执行授权边界

- 本方案 Phase B 对旧机**只读**（rsync 拉取、pg\_dump、docker save），属授权诊断范围，可直接执行。

- Phase C1 起涉及旧机停服务、新机部署变更，**逐项需用户明确授权**后执行。

- 迁移执行人为 Agent 时，每步命令与验证输出回传确认，不做方案外操作。
