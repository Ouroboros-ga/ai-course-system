### 5.1 judge0 迁移 + cgroup v2 兼容（已跑通判题）

背景：新机内核 5.15 为 **cgroup v2**，官方 `judge0/judge0:1.13.1` 内置 isolate 1.8.1 **不支持 v2**，判题报
`Failed to create control group /sys/fs/cgroup/memory/box-1/` 或 `Read-only file system / Permission denied`
（实测 default / SYS_ADMIN / privileged 均无效 —— 容器对宿主只读 cgroup v1 树无权写入）。

处理（经用户授权引入第三方 fork `mrkushalsm/judge0`，接受 `privileged`）：

1. fork 源码 `isolate-cgroup-v2.patch` 仅把 `SYS_quotactl_fd` 切换到 `quotactl()`（无后门、不削弱隔离）；isolate 升级到 **2.2.1**（唯一兼容 cgroup v2 版）。
2. 在 `/opt/smartcarb/build/judge0_mrk` 构建（tarball 解压代替 git clone，绕开容器内 GitHub HTTP/2 framing 错误；修复脚本 CRLF→LF + chmod +x，修复 entrypoint 元数据），产镜像 `judge0/judge0:cgv2-final`。
3. 重建 `judge0-server` / `judge0-worker`：`--privileged --user judge0`，接 `judge0_net`(内网) + `judge0_api`(外网) 双网络，端口 `-p 127.0.0.1:2358:2358`。
4. **判题实测成功**：`POST /submissions?wait=true`（Python）返回 `status=Accepted`、`stdout=Hello from cgroup v2 judge0`、time≈0.02s。
5. 后端 `JUDGE0_API_URL=http://127.0.0.1:2358`（默认配置），日志确认 `GET http://127.0.0.1:2358/system_info 200 OK`。

> ⚠️ **安全提示**：此方案依赖 `privileged` 运行 judge0 沙箱容器（isolate 需直接操作宿主 cgroup）。judge0 是执行不可信代码的沙箱，`privileged` 扩大了容器权限面（若隔离被突破影响面更大）。这是官方在当前 cgroup v2 宿主上跑通判题的必要前提。若后续更关注安全，可评估升级到官方未来支持 cgroup v2 的版本，或改用海外/更可控环境。

### 5.3 前端资源加载 / HTTP2 协议错误 / gzip

- 用户浏览器报 `net::ERR_HTTP2_PROTOCOL_ERROR`、动态 import 失败、`reportAllChanges` 报错、页面卡顿。
- 排查结论：服务器 dist 干净（无 `__VUE_PROD_DEVTOOLS__`/`reportAllChanges`）；237 个 chunk 全在盘上。`ERR_HTTP2_PROTOCOL_ERROR` 是浏览器与服务器单条 HTTP/2 连接被中断（本地扩展/网络干扰），非代码问题。
- 处理：nginx `listen 443 ssl` 降级为 **HTTP/1.1**（移除 `http2`）；开启 gzip（`gzip_types`/`gzip_vary`/`gzip_proxied any`/`gzip_comp_level 6`），JS/CSS 变为 `Content-Encoding: gzip`。原配置已备份 `smartcarb.bak.*`。

### 5.5 本次新增的经验

- 跨机传输 judge0 镜像时，`-p` 端口映射在 `Internal=true` 的 `judge0_net` 下**不生效**；需给 server 额外接非 internal 的 `judge0_api` 网络才能发布 2358。
- Windows/scp 打包源码会丢失 Unix 可执行位并以 CRLF 写入；镜像内脚本需 `chmod +x` + CRLF→LF，且文件属主若非运行用户时需以 root 修复。
