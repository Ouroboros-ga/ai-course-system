### 1.1.1 分支更新执行结果（2026-09-08 14:35）

**已完成**：本地 `dev-liu` 已快进至 `1f92c176`（与远端一致）。

| 步骤 | 结果 |
|---|---|
| 确认本地 `dev-liu` 无远端独有提交 | ✅ `git log origin/dev-liu..dev-liu` 为空，快进无损失 |
| 更新本地分支 | ✅ `dev-liu` → `1f92c176`（2026-09-08） |
| 更新后落后数 | ✅ `git rev-list --count dev-liu..origin/dev-liu` = 0 |

**⚠️ 环境异常（需留意，非仓库问题）**：

1. 执行 `git fetch --all --prune` 后，本地 `origin/*` 远端跟踪引用被**批量删除**（含 `origin/dev-liu`、
   `origin/feature/xh202620` 等 7 个），仅剩 `dev-amq`/`dev-ffone`/`dev-kwumn`/`dev-will`/`master`/`stable`。
2. 用 `git ls-remote --heads origin` 核验：**远端 gitee 上 `dev-liu` 分支正常存在**，HEAD 正是
   `1f92c1760c2344b9fbe3358bcc1943d113760c99`。即分支没被删，是本地引用被 prune 掉了。
3. 重新 `git fetch origin "+refs/heads/*:refs/remotes/origin/*"` 时，git 报告
   `* [new branch] dev-liu -> origin/dev-liu` 成功，**但引用未落盘**：
   `.git/refs/remotes/origin/` 目录不存在、`.git/packed-refs` 未更新，随后 `git log origin/dev-liu` 报
   `unknown revision`。`git update-ref refs/remotes/origin/dev-liu` 同样无效。
4. 根因判断：当前执行环境对 `.git/refs/remotes/` 无写入权限（或写入被沙箱拦截）。
   `refs/heads/*`（本地分支）可正常写入，故改用 `git update-ref refs/heads/dev-liu 1f92c176` 完成更新。

**影响与后续**：本地分支已是最新，可正常工作；但 `origin/dev-liu` 这类远端跟踪引用在本环境暂时无法重建，
如需对比"本地 vs 远端"，改用 `git ls-remote --heads origin` 直接查远端，或直接用已确认的 SHA。
**建议团队成员在正常环境（非本沙箱）执行一次 `git fetch origin` 恢复远端跟踪引用。**

### 8.2 问题⑥：垂类模型未实际训练

> ### ⚠️ 2026-09-08 15:10 上机实证：服务器**无 GPU**
>
> `nvidia-smi` 命令不存在（未安装驱动/无 NVIDIA 设备），主机为 15Gi 内存的普通云主机。
> **结论：路径 A（本机 GPU 训练）在这台服务器上不可行**——需外部 GPU 资源（自有显卡机、云 GPU 按量实例）
> 或改用 MaaS。这一硬约束直接改变三条路径的可行性排序，见下表修正。

#### 现状（代码与文档事实）

- 数据集：**197 训练 + 31 评测**（112 知识节点 + 106 关系 + 10 基准问 = 228 条，90/10 划分后评测并入基准）。
- **防污染设计**：评测基准 10 问**只进 eval 不进 train** —— 保证"基座 vs 微调"对比不被记忆污染，
  这个设计是对的，也是能在答辩上讲的点。
- 训练脚本：`train_lora.py` 为完整 PEFT LoRA 实现（ChatML 模板化、prompt 段 loss 掩蔽、
  按 epoch 保存 adapter），默认基座 `Qwen/Qwen2.5-7B-Instruct`，`batch=2`、bf16，
  **缺 CUDA 时退出码 2 fail-closed**（不假装训练成功）。
- 显存门槛：README 明示 **≥16GB**；当前环境无 GPU，**训练未执行**。

#### 为什么这件事比看起来更关键

赛题全称是《面向一流学科建设的**学科垂类大模型**与创新应用开发》——**"垂类大模型"是题眼**。

我们目前实际交付的是：通用基座 DeepSeek + 学科知识库 RAG（112 节点）+ 多 Agent 应用。
这构成"学科垂类**应用**"，但严格说不构成"学科垂类**模型**"。评委若较真，这里是能被正面质疑的点，
且直接关系**内容质量度 20 分**与**技术实现度 20 分**。

#### 三条路径对比

| 路径 | 做法 | 成本 | 得分效果 | 风险 |
|---|---|---|---|---|
| **A. GPU 训练** | 16GB+ 显存跑 `train_lora.py`（197 条、3 epoch） | 🔴 **本机不可用（无 GPU）**；需外部 GPU，7B LoRA 约 1–3 小时 | 最强：真实 adapter + 基座/微调对比数据 | 依赖外部资源；训练失败有时间风险 |
| **B. 星火 MaaS 微调** | 提交数据集到讯飞 MaaS，拿 ServiceID | 需账号与授权，可能付费 | 强：且**贴合发榜单位生态**（讯飞），叙事额外加分 | 时间不可控；需授权 |
| **C. 管线 + RAG 口径如实申报** | 不训练，材料说明"管线可复现 + 基座 DeepSeek + 学科 RAG 增强" | 零 | 中：诚实但"垂类模型"论证偏弱 | 评委看重模型本身时丢分 |

#### 建议

- **首选 B（星火 MaaS）** —— 上机确认本机无 GPU 后，A 需额外找资源，B 成为现实最优解。
  它同时解决"垂类模型"与"深度结合讯飞"两个得分点，197 条数据规模小，MaaS 微调通常数小时内完成。
  **建议今天就提交数据、拿 ServiceID**，这是唯一能同时补上两块 20 分的动作。
- **A 仅在能快速拿到外部 GPU 时考虑**（云 GPU 按量实例跑 1–3 小时亦可，成本可控）；
  没有现成 GPU 渠道就不要在它上面耗时间。
- **若时间不足或 B 走不通**：走 **C**，但叙事必须改成主动技术选择而非缺失——
  "学科知识以 RAG + 知识图谱方式注入，保证可追溯、可更新、可审计；
  微调管线已完整交付并可复现，但**在小样本场景下刻意不以微调固化知识**，
  以避免灾难性遗忘与知识过期"。
  **这个论点技术上站得住**（小样本微调确实容易损伤通用能力并固化知识），不是遮掩。
- **无论选哪条，都不要隐藏未训练的事实** —— AGENTS.md §4.2 伪实现红线与材料 06 的诚实边界
  都禁止把"管线可复现"表述成"已完成微调"。
- **补救动作（C 路径下强烈建议）**：把评测用例从 10 条扩到 20–30 条并公布通过率，
  用**应用层质量证据**补**模型层缺失**，稳住内容质量度 20 分。
