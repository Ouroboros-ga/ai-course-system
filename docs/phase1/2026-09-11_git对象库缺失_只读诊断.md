# 7. 仍在生效的缺陷（**这是重点**）

## 7.1 现象

| 观察 | 证据 |
|---|---|
| 新建的 ref **文件**会被清除 | `git update-ref refs/heads/feature/product1-integration d732491d...` 返回 0，随后 `git rev-parse` 即 "Needed a single revision" |
| **reflog 却留下来了** | `.git/logs/refs/remotes/github/{dev-liu,master,dev-main,...}` 全在，而 `.git/refs/remotes/github/` 是空的 |
| `git fetch` 报 `* [new branch]` | 说明 fetch 认为写入成功，实际落盘后被清 |
| 固化进 `packed-refs` 的引用能存活 | 17→20 条后，`dev-liu` 与两个标签稳定可解析 |

## 7.2 最可能的根因

「**loose ref 被删、`packed-refs` 未更新**」正是 `git pack-refs`（`git gc` 会调用）
**被中断**的典型残留：它先写 `packed-refs`，随后删 loose ref；若卡在中间，
就得到「ref 文件没了、packed-refs 是旧的」。

这与最初损坏的形态完全同构：

```text
删除 loose refs（refs/heads 空）
+  pack 文件缺失只剩 .idx
+  commit-graph 指向已不存在的对象
= 一次被打断的 git gc / repack
```

# 8. 根因修正：不是「被清除」，是**子目录创建不落盘**（实测，取代 §7.2）

§7.2 把 `refs/` 空目录归因为「ref 被删」，**这个判断不准**。做了隔离实验后，
现象精确得多：

| 实验 | 结果 |
|---|---|
| 写**顶层** ref `refs/heads/_probe_oj` | ✅ 解析成功，文件存在 |
| 写**嵌套** ref `refs/heads/feature/_probe_nested`（需新建子目录） | ❌ 返回 0，但解析失败 |
| 手工 `mkdir -p .git/refs/heads/feature` | **返回 0，且当场 `ls` 能看到该目录** |
| mkdir 之后**立刻**重试嵌套 ref | ❌ **仍然失败** |
| 几秒后再看 | **刚建的 `feature` 目录已不存在** |

**结论**：`update-ref` 对嵌套 ref 返回 0 却不落盘；`.git/refs/` 下**新建的子目录
无法存活**（`mkdir` 报成功，随后消失）。而**顶层 ref 文件与 `packed-refs` 正常**。

这也解释了 §7.1 里最费解的观察——为什么 reflog 在、ref 文件不在：
git 会为嵌套 ref 在 `.git/logs/refs/...` 建目录并写 reflog，
但 `.git/refs/...` 那一侧的目录活不下来。

## 8.1 实际影响（比 §7 轻得多）

|---|---|

  若仍失败，说明子目录在两次命令之间已经消失。
