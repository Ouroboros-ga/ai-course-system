## 讨论一：统一解析、课程建设与发布

```text
#0
我对上传文件流程理解：
添加一个简单备课agent，websearch，rag原文可信检索。 作为一个小悬浮窗，教师可以对话让agent生成”建设“页面全部文字内容。但都要有人类审核，（即生成之后新编辑文字有个绿框，删除文字有红框，框上面”“接受”"拒绝"）。
文件上传（各种格式）--解析服务把他们解析为统一格式文本，--（同步1）文本切片向量化，存储向量库，同步上传知识图谱，形成可信rag。agent同步对知识图谱节点（每个知识点为一节点）文本内容进行审核，优化更适合阅读浏览，便于eduagent推荐检索；（同步2）agent对这份文本进行知识点与结构划分（当且仅当是.pptx储存页码与知识点映射）。--（同步1）agent生成这份知识点讲解稿 ；（同步2）转为markdonn储存在课程绑定资料库。 --页面映射如果源文件ppt则按照映射自动分配，可有教师手动调整，否则不显示映射（docx，pdf等），推荐教师再上传ppt课件，或通过agent一键生成（agent接入科大讯飞aippt接口），ppt生成依据是经过教师审核的知识点结构，与讲解稿。--教师媒体生成则是选择数字人预设，也可选择平台默认数字人形象，通过服务后台匹配数字人动作与语音，对齐时间戳。在学生首次调用时把音频文件和数字人素材发到本地实时合成。


你的整体思路可行，而且比当前“旧讲稿链 + 新 Evidence 链并存”更符合实际备课过程。我建议按你的决定收口，但修正三个语义：

- Agent 不是“审核者”，而是“二次优化建议者”；最终审核者始终是教师。
- Markdown 是展示与编辑产物，不是唯一事实源。原始页码、坐标、证据来源仍保存在 `DocumentBlock/Evidence`。
- 图谱和 RAG 可以自动生成，但解析阶段生成的是草稿版本；课程发布后才成为学生问答和推荐使用的正式版本。

## 收口后的统一流程

```text
统一文件上传
→ 对象存储
→ 格式转换与解析
→ DocumentIR / DocumentBlock
├─ 可信 RAG：切片、向量、原文证据
├─ 图谱候选：知识点、关系、节点说明
├─ TeachingStructureBuilder：课程结构候选
└─ TeachingScriptBuilder：讲授脚本候选
       ↓
备课 Agent 提出增删改建议
       ↓
教师接受 / 拒绝 / 手动编辑
       ↓
保存课程草稿
       ↓
可选 PPT 生成、页面映射、TTS、数字人媒体
       ↓
教师手动发布
```

## 1. 统一上传入口

正式保留：

```text
POST /api/v1/document/course-imports
```

旧 `/document/upload` 改成兼容转发，最终删除其同步解析、直接写 `CourseScript`、自动 TTS 等旧逻辑。

上传成功后立即返回：

```json
{
  "course_id": 85,
  "task_id": "task_xxx",
  "run_id": "dpr_xxx",
  "status": "processing"
}
```

浏览器离开不影响当前解析任务。Demo 阶段可以接受后端重启导致任务中断，但重启后至少要把残留的 `running` 标记成：

```text
interrupted
解析因服务重启中断，请重新解析
```

不用自动恢复，但不能永远显示“解析中”。

## 2. 正式解析矩阵

按你确认的策略执行：

| 输入 | 处理方式 |
|---|---|
| PPTX | NativePptx 提取结构；图片型页面用 PaddleOCR |
| PDF | PdfPlumber 提取原生文本；每页渲染并执行 PaddleOCR，再进行结果融合 |
| 图片 | PaddleOCR 主解析 |
| DOCX | PythonDocx 提取语义结构，同时转 PDF 获取页码、坐标及 OCR |
| DOC | LibreOffice 转 PDF，再执行 PdfPlumber + PaddleOCR |

PaddleOCR 使用独立解析服务，避免污染主后端 Python 3.12 环境：

```text
Backend
→ DocumentOcrPort
→ 独立 PaddleOCR 服务
```

主后端只消费稳定 JSON，不依赖 Paddle 运行时。

## 3. 统一解析格式

所有格式最终进入统一 `DocumentIR`：

```text
document_id
material_version_id
blocks[]
  block_id
  block_type
  text
  page_or_slide
  bbox
  reading_order
  source_kind
  confidence
  content_hash
  provider_version
```

同时生成一份适合教师阅读的 Markdown，但必须保留：

```text
Markdown 段落
→ source_block_refs
→ 原文件页码/幻灯片页
→ bbox
```

否则 Markdown 编辑后将无法支撑可信引用。

## 4. 可信 RAG 与图谱

解析完成后并行执行。

### RAG

```text
DocumentBlock
→ 语义切片
→ embedding
→ 课程隔离向量索引
→ 绑定 Evidence 引用
```

每个检索结果必须返回：

```text
course_id
chunk_id
evidence_refs
material_version_id
page
text
score
```

教师备课 Agent 可以查询草稿索引；学生 EduAgent 只能查询已发布课程索引。

### 知识图谱

```text
DocumentBlock
→ 知识点候选
→ 关系候选
→ 节点说明候选
→ Agent 提出阅读优化建议
→ 教师审核
```

建议区分：

```text
GraphDraftSnapshot
GraphPublishedSnapshot
```

Demo 不需要复杂发布编排，但必须避免教师仍在编辑时，学生突然读到半成品图谱。

## 5. TeachingStructureBuilder

它负责从解析文本生成第一版课程结构：

```text
课程
├─ 章
│  ├─ 节
│  │  ├─ 知识点
│  │  ├─ 示例
│  │  └─ 练习建议
```

输出必须包含：

```text
title
node_type
parent_id
order_index
source_block_refs
page_range
generation_reason
confidence
```

对应建设页：

```text
/app/course/{course_id}/build/structure
```

页面需要从现在的“只读旧 ScriptNode”改成真正编辑器，至少支持：

- 新增、删除、重命名；
- 拖动排序；
- 修改父级；
- 保存草稿；
- 查看来源；
- 接受或拒绝 AI 修改；
- 教师锁定节点。

## 6. 讲授脚本

结构形成后，由 AI 自动生成第一版讲解稿：

```text
审核中的课程结构
+ 对应 Evidence
+ 教师课程风格配置
→ TeachingScriptCandidate
```

对应：

```text
/app/course/{course_id}/build/scripts
```

每个节点的讲稿应支持：

- 直接编辑并保存；
- AI 重写、缩短、扩展；
- 选择解释风格；
- 查看引用来源；
- 接受、拒绝 AI 建议；
- 锁定教师版本；
- 保留简单版本历史。

自动生成后仍是草稿，但不要求每一段都单独点击“通过”才能保存。更实用的交互是：

```text
AI 初稿默认进入编辑器
教师可直接修改
最终点击“确认本步骤”
```

后续 Agent 提出的改动才使用绿色/红色差异框。

## 7. 备课 Agent

小悬浮窗的设计合理。它应通过受控 Tools 修改草稿，而不是直接写数据库：

```text
DraftRagSearchTool
WebSearchTool
GraphDraftTool
StructureDraftTool
ScriptDraftTool
PptGenerationTool
MediaGenerationTool
```

工作流：

```text
教师：“把第三章改得更适合零基础学生”
→ Agent 读取草稿结构和可信 Evidence
→ 生成 Patch Proposal
→ 页面显示修改差异
→ 教师逐项或批量接受/拒绝
→ 接受后写入新草稿版本
```

Patch 应是结构化数据：

```json
{
  "proposal_id": "proposal_x",
  "operations": [
    {
      "operation": "replace",
      "target": "script_node_12.content",
      "before": "原内容",
      "after": "建议内容",
      "reason": "降低术语密度",
      "evidence_refs": ["ev_01"]
    }
  ]
}
```

前端表现：

- 新增内容：绿色边框；
- 删除内容：红色边框和删除线；
- 修改内容：左右或行内 Diff；
- 每项提供接受、拒绝；
- 页面顶部提供全部接受、全部拒绝；
- 教师手动编辑后，以教师内容为准。

WebSearch 的内容必须标记为“外部补充资料”，不能伪装成课程原文。

## 8. 页面映射和 AI PPT

你的规则可以冻结为：

- PPTX：自动生成知识点—幻灯片映射，允许教师调整。
- PDF、DOCX、DOC：保留 Citation 页码，但建设页面不显示“教学 PPT 映射”步骤。
- 没有 PPT 时提示教师：

```text
上传现有 PPT
或
根据已确认的课程结构和讲授脚本生成 PPT
```

科大讯飞 AI PPT 输入应只使用教师已确认的数据：

```text
确认后的课程结构
+ 确认后的讲稿
+ 课程主题/风格
→ AI PPT 任务
→ PPT 草稿
→ 教师预览与确认
→ 新 SourceMaterialVersion
→ 再次解析并建立页映射
```

生成出来的 PPT 不能绕过解析链直接成为正式课件。

## 9. 媒体和数字人

教师确认讲稿和页映射后：

```text
讲稿
→ 科大讯飞 TTS
→ 句子/词级时间戳
→ 数字人动作与表情计划
→ MediaTimelineCue
```

首次播放时向浏览器发送：

- 音频；
- 数字人资产包版本；
- 动作/口型时间轴；
- PPT 页面时间轴；
- 字幕与讲稿。

浏览器按之前确定的三档运行：

```text
自动模式：浏览器实时合成
低资源模式：简化动作和帧率
兼容模式：预生成视频或静态头像 + 音频
```

数字人 Provider 必须可替换，课程数据只绑定 `avatar_preset_id` 和资产版本，不绑定具体开源实现。

## 10. 简化发布模型

同意 Demo 只保留：

```text
DRAFT
PUBLISHED
```

教师或管理员手动切换。但发布动作仍应检查最低条件：

- 有课程结构；
- 有讲授脚本；
- 源文件解析成功；
- 没有仍在运行的关键任务。

图谱、媒体可以暂时不是发布的硬条件，不存在时学生端诚实降级。

## 11. 历史课程处理

按你的决定：

- 删除“历史课程自动迁移”路线；
- 旧课程不自动补建；
- 新统一上传路径完成后，重新上传原文件生成新课程；
- 原课程暂时保留，只读或标记为旧版；
- 不把旧 `CourseScript/ScriptNode` 自动混入新课程。
