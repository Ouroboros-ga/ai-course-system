# CS 语料 RAG 扩量方案（2026-09-09）

> 依据：cs-textbooks 首批上线实测（[修复计划 §7](规划完成度修复计划_2026-09-09.md)）＋服务器资源核查。
> 结论：**ANN 是扩量的前置门**（当前精确扫描在 4M 块量级不可用）；**磁盘是第二约束**；
> embedding 是长尾后台作业（全量约 6 天，worker 已常驻低优先级跑）。

## 1. 实测基线

| 项 | 实测值 | 来源 |
|---|---|---|
| 分块产出 | 72 篇 / 3.2MB → **3899 块**（≈1218 块/MB，≈54 块/篇） | cs-textbooks 首批 |
| 向量化吞吐 | 244/244 分片成功，**≈7–8 块/秒**（单进程 CPU，bge-small-zh 512 维） | worker 实跑 |
| 检索延迟 | 精确扫描 **5–7 秒/查询 @ 3899 块**（随成员数线性增长） | 6 题样本 1m11s |
| 服务器 | 4 核 / 15GB（可用 13）/ 磁盘**剩 29GB** | `nproc`/`free`/`df` |
| PG | 16.14，**pgvector 扩展已安装**；`discipline_corpus_vectors.embedding` 现为 JSON 列 | 只读查询 |

**瓶颈定位**（`corpus_search.py::_vector_recall`）：每查询把 release 内**全部**向量行拉回（无 LIMIT）并在 Python 逐行 `_cosine`；无 pgvector 列、无 HNSW、`ann_index` 硬编码 `none`。

## 2. 容量测算（按首批比例外推）

| 来源 | 文档数 | 原始 | 估算块数 | 向量化时长 |
|---|---|---|---|---|
| textbooks | 72 | 3.2MB | 3.9k | 已完成 |
| zhwiki | 22,770 | 92MB | ~112k | ~4h |
| enwiki | 117,779 | 699MB | ~850k | ~30h |
| rfc | 9,824 | 554MB | ~675k | ~24h |
| arxiv | 待核 | 2.1GB | ~2.5M | ~90h |
| **合计** | | ~3.4GB | **~4.1M** | **~6 天（后台）** |

存储需求：向量 4.1M×512×4B ≈ **8.4GB**（pgvector）＋ JSON 列约 16GB（若保留）
＋ 正文存储 ~10GB ＋ FTS ~3GB → **超出 29GB 余量**，必须先扩容或改变存储策略。

## 3. 三阶段方案

### P0（前置门）：ANN 检索改造

复用仓库现成件，改动最小集：

| # | 改动 | 位置 |
|---|---|---|
| 1 | 模型加 `embedding_vec` 列（复用 `PgVectorType`，SQLite 降级存文本） | `backend/app/models/discipline_corpus_index_model.py:27-45`（模板：`research_workspace_model.py:25-59`） |
| 2 | 方言感知迁移：`CREATE EXTENSION IF NOT EXISTS vector` ＋ `USING hnsw (embedding_vec vector_cosine_ops)` | 新增 `backend/alembic/versions/*.py`（DDL 先例：`knowledge_data/corpus/build_corpus_embeddings.py:176-185`） |
| 3 | 写入侧同写两列（JSON 保留兼容 SQLite/旧路径） | `corpus_embedding.py::VectorCache.put/put_many:433-480` |
| 4 | **唯一查询改造点**：`ORDER BY embedding_vec <=> :q`，join members 过滤 release＋`model_fingerprint`；保留 fail-closed/降级与指纹校验 | `corpus_search.py::_vector_recall:306-341` |
| 5 | `ann_index` 如实改实际值（现硬编码 `none`/`exact-member-filtered`） | `corpus_index.py:644-651`、`:657` |
| 6 | 回退分支：ANN 不可用时仍走精确路径（保留现有代码） | 同上 |

**验收**：`verify_corpus_rag.py` 的 `latency_ms.p50/p95/max` 前后对照（目标 p95 < 200ms @ 4M 量级）；
`EXPLAIN (ANALYZE, BUFFERS)` 证明命中 HNSW；过滤后不足 top-k 的报数语义按计划 §151（有界扩大召回）。

### P1：容量与存储（与 P0 并行）

- **磁盘**：至少扩到 **80GB 可用**（当前 29GB）；或按源分批并在 PG 上停写 JSON 列。
- **决策点**：PG 是否保留 JSON 列——保留＝兼容 SQLite 测试与旧路径，代价约 16GB；
  停写＝省空间，但需保证 SQLite 部署与本地测试仍能工作（列可空/回填脚本）。

### P2：分批扩量执行（worker 常驻自动跑）

- 每源一个构建：`create-build --scope <set> --chunker-version <冻结值> --max-chunks <预算>`
  （`--chunker-version` 必须带，避免多套分块混入，见首批缺陷 #3）；
- 顺序：**zhwiki → enwiki → rfc → arxiv**（小到大，先验证质量再压量）；
- 每源完成后：`build --from-build` → `validate` → `verify_corpus_rag` → `activate`
  （旧 release 保留，可回切）；
- 两个单元已常驻：`smartcarb-corpus-embedding`（127.0.0.1:8310，指纹 `emfp_f29bec2e…`）
  与 `smartcarb-corpus-worker`（Nice=10 / IOSchedulingClass=idle，空闲退出轮询 60s），
  不抢 8000 端口查询资源。

## 4. 风险与止损

| 风险 | 止损 |
|---|---|
| ANN 改造失败 | 保留精确分支，`ann_index` 如实记 `none`，不伪装 |
| 磁盘不足 | worker `max_disk_bytes` 预算到顶暂停（可恢复、不伪成功）；扩容前不启动 arxiv |
| 单源质量差 | 每源 release 独立验收后才切 head；旧 release 可 `activate` 回切 |
| embedding 服务故障 | 服务 fail-closed 退出码 2；worker 走 HTTP 失败重试，不静默跳过 |

## 5. 待决

1. **磁盘扩容方式**（云盘扩容 vs 分源清理后滚动）——决定 arxiv 是否在本轮启动。
2. **PG 上是否停写 JSON 向量列**（省约 16GB）——影响 SQLite 部署与本地测试路径。
3. 扩量顺序是否按"zhwiki 先行验收质量，再放量 enwiki/rfc/arxiv"。
