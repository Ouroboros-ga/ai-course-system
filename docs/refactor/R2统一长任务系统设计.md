# R2 统一长任务系统设计

更新时间：2026-07-09

本设计只用于 R2A：统一长任务系统设计与现状盘点。不在本阶段落地业务迁移，不新建数据库表，不修改公开 API，不修改前端轮询方式，不引入 Celery、Redis 或 RabbitMQ。

## 为什么需要统一长任务系统

当前系统有多类耗时任务：文档解析、脚本生成、PPT 生成、TTS、数字人视频、声音复刻、泛雅同步、远程视频拉取等。它们的状态表达不一致：

- `backend/app/models/course_model.py::ParseStatus` 使用 `pending/processing/completed/failed`。
- `backend/app/models/video_generation_model.py::GenerationStatus` 使用 `pending/tts_synthesizing/tts_completed/dh_generating/completed/failed`。
- `backend/app/models/asset_model.py::CloneStatus` 使用 `none/pending/success/failed`。
- `backend/app/services/ppt_generation_service.py::PPTTaskResult` 使用 `pending/done/failed/timeout`。
- `backend/app/api/v1/endpoints/document.py` 的 TTS 批量状态使用内存字典 `tts_generation_status`。

这些状态都服务于相似的问题：启动、运行、成功、失败、超时、部分成功、查询、记录错误。R2 的目标不是一次迁移所有业务，而是先设计一个兼容层，让后续迁移能逐批完成，并且不改变现有 API、数据库结构和用户可见行为。

## R1 adapter 与 R2 task runner 的关系

R1 adapter 解决“外部服务调用结果如何统一表达”：

- `AdapterResult.success`
- `AdapterResult.data`
- `AdapterResult.error_code`
- `AdapterResult.error_message`
- `AdapterResult.provider`
- `AdapterResult.raw`
- `AdapterResult.duration_ms`

R2 task runner 解决“业务长任务如何统一表达和落到现有状态字段”：

- R1 只关心一次外部服务调用，比如 `PPTAdapter.wait_for_completion` 或 `DigitalHumanAdapter.generate_video`。
- R2 关心业务任务生命周期，比如 PPT 生成从 LLM 扩展、创建 sid、轮询、下载，到生成课程或失败；数字人任务从 TTS、数字人生成，到写 `VideoGenerationTask`。
- R2 不替代 R1。R2 的 `TaskRunner.run` 可以接收 R1 的 `AdapterResult`，再映射为 `TaskResult` 和业务表状态。

建议关系：

```text
endpoint
  -> service
    -> TaskRunner
      -> R1 adapter
        -> external client/fake client
```

本阶段不要求所有 service 都套入该结构。R2B 先选择数字人和 PPT。

## TaskStatus 设计

建议统一状态枚举：

| TaskStatus | 含义 | 可映射的现有状态 |
|---|---|---|
| `PENDING` | 已创建，尚未实际执行 | `ParseStatus.PENDING`、`GenerationStatus.PENDING`、`CloneStatus.PENDING` 的创建前阶段 |
| `RUNNING` | 正在执行 | `ParseStatus.PROCESSING`、`GenerationStatus.TTS_SYNTHESIZING/DH_GENERATING`、TTS 内存 `processing` |
| `SUCCEEDED` | 完整成功 | `ParseStatus.COMPLETED`、`GenerationStatus.COMPLETED`、`PPTTaskResult.status == "done"`、`CloneStatus.SUCCESS` |
| `FAILED` | 明确失败 | `ParseStatus.FAILED`、`GenerationStatus.FAILED`、`PPTTaskResult.status == "failed"`、`CloneStatus.FAILED` |
| `CANCELLED` | 用户或系统取消 | 当前无现有等价状态，先保留设计，不在 R2B 实现 |
| `TIMEOUT` | 外部服务或长轮询超时 | `PPTTaskResult.status == "timeout"`、R1 `AdapterErrorCode.TIMEOUT` |
| `PARTIAL_SUCCESS` | 批量任务部分成功 | TTS 批量内存状态 `partial`、批量视频生成部分节点失败 |

兼容原则：

- 对外 API 仍返回原字段和值，例如 `/api/v1/video-gen/task/{task_id}` 仍返回 `GenerationStatus` 的字符串。
- TaskStatus 是内部归一化，不直接替换生产数据库枚举。
- `TIMEOUT` 在已有业务字段无法表达时，可落为业务 `failed`，同时在 `error_message` 或 `TaskResult.error_code` 保留 `timeout`。

## TaskResult 设计

建议字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| `success` | bool | 业务任务是否成功 |
| `status` | TaskStatus | 统一任务状态 |
| `data` | Any | 业务成功结果，例如 `VideoGenerationTask`、`PPTTaskResult` |
| `error_code` | str \| None | 统一错误码，可复用 R1 adapter 错误码 |
| `error_message` | str \| None | 可解释错误信息 |
| `provider` | str \| None | 外部服务提供方，例如 `xfyun_ppt`、`digital_human`、`tts` |
| `raw` | Any | 原始 adapter 或业务返回 |
| `duration_ms` | float | 本次执行耗时 |
| `started_at` | datetime \| None | 执行开始时间 |
| `finished_at` | datetime \| None | 执行结束时间 |

建议错误码优先复用 R1：

- `timeout`
- `service_unavailable`
- `malformed_response`
- `business_failure`
- `unknown_error`

## TaskContext 设计

建议字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| `task_id` | str \| int \| None | 现有任务 ID，例如 `VideoGenerationTask.id`、讯飞 `sid`、`docling_doc.id` |
| `task_type` | TaskType | 任务类型 |
| `user_id` | int \| None | 当前用户 |
| `course_id` | int \| None | 课程 ID |
| `node_id` | int \| None | 脚本节点 ID |
| `provider` | str \| None | 外部服务名 |
| `input_summary` | str \| None | 输入摘要，不记录敏感全文 |
| `metadata` | dict | 兼容现有业务的补充信息 |

安全原则：

- 不记录 API Key、Token、真实密钥。
- 不把整段课件或学生隐私原文写进 `input_summary`。
- 测试中可用 fake metadata 验证调用关系。

## TaskRunner 最小接口

建议接口：

```python
class TaskRunner:
    async def create_task(self, context: TaskContext) -> TaskResult: ...
    async def mark_running(self, context: TaskContext) -> TaskResult: ...
    async def mark_progress(self, context: TaskContext, progress: dict) -> TaskResult: ...
    async def mark_succeeded(self, context: TaskContext, data=None) -> TaskResult: ...
    async def mark_failed(self, context: TaskContext, error_code: str, error_message: str) -> TaskResult: ...
    async def run(self, context: TaskContext, operation) -> TaskResult: ...
    async def query_status(self, context: TaskContext) -> TaskResult: ...
```

R2B 可先实现更小子集：

- `run`
- `mark_succeeded`
- `mark_failed`
- `query_status`

实现约束：

- 不引入 Celery/Redis/RabbitMQ。
- 不要求新建统一任务表。
- 不改变现有 API 响应结构。
- 不改变 `VideoGenerationTask`、`DoclingDocument`、`TeacherAsset` 等生产表结构。

## 如何兼容已有任务表

兼容层不直接改表，而是提供映射函数：

| 现有对象 | 现有字段 | TaskStatus 映射 |
|---|---|---|
| `DoclingDocument` | `status=ParseStatus.PENDING` | `PENDING` |
| `DoclingDocument` | `status=ParseStatus.PROCESSING` | `RUNNING` |
| `DoclingDocument` | `status=ParseStatus.COMPLETED` | `SUCCEEDED` |
| `DoclingDocument` | `status=ParseStatus.FAILED` | `FAILED` |
| `VideoGenerationTask` | `status=GenerationStatus.PENDING` | `PENDING` |
| `VideoGenerationTask` | `status=TTS_SYNTHESIZING/TTS_COMPLETED/DH_GENERATING` | `RUNNING` |
| `VideoGenerationTask` | `status=COMPLETED` | `SUCCEEDED` |
| `VideoGenerationTask` | `status=FAILED` | `FAILED` |
| `PPTTaskResult` | `status="done"` | `SUCCEEDED` |
| `PPTTaskResult` | `status="failed"` | `FAILED` |
| `PPTTaskResult` | `status="timeout"` | `TIMEOUT` |
| `TeacherAsset` | `clone_status=SUCCESS` | `SUCCEEDED` |
| `TeacherAsset` | `clone_status=FAILED` | `FAILED` |
| `TeacherAsset` | `clone_status=PENDING` | `RUNNING` |
| TTS 批量内存状态 | `completed` | `SUCCEEDED` |
| TTS 批量内存状态 | `partial` | `PARTIAL_SUCCESS` |

如果现有表无法表达 `TIMEOUT`，生产字段仍写原有失败值，例如 `failed`，但 `TaskResult.error_code="timeout"` 必须保留在错误信息或测试断言中。

## 如何保持 API 不变

R2 的兼容层只存在于 service 内部：

- `/api/v1/video-gen/task/{task_id}` 仍返回 `_task_to_dict(task)`。
- `/api/v1/ppt/generate-sync` 仍按 `result.status != "done"` 返回 `code=500`。
- `/api/v1/ppt/task/{sid}` 仍返回讯飞进度 `data`。
- `/api/v1/document/course/{course_id}/tts-status` 仍返回当前 `status/total/completed/errors`。

任何统一状态都不直接暴露给前端，除非后续单独设计兼容版本字段。

## success / timeout / service_unavailable / malformed_response / business_failure

R2 与 R1 的错误关系：

| R1 AdapterErrorCode | TaskStatus | 业务落地建议 |
|---|---|---|
| success | `SUCCEEDED` | 保持原成功行为 |
| `timeout` | `TIMEOUT`；若现有 DB 无 timeout 则业务状态写 failed | error_message 包含超时原因 |
| `service_unavailable` | `FAILED` | endpoint 可保持原 503 或 service 失败记录 |
| `malformed_response` | `FAILED` | 标记为上游响应异常，不当作业务成功 |
| `business_failure` | `FAILED` | 结构化响应可解析但业务失败，不抛网络异常模拟 |
| unexpected exception | `FAILED` | error_code=`unknown_error` 或异常分类 |

测试要求：

- fake 必须能稳定触发以上模式。
- 不通过真实外部服务触发。
- 不把 business_failure 伪装成 malformed response 或网络异常。

## 如何记录进度和错误

短期兼容策略：

- 数字人：继续写 `VideoGenerationTask.status/error_message/retry_count/updated_at`。
- PPT：继续返回 `PPTTaskResult.status/error`，异步路径继续写 `DoclingDocument.status/error_message`。
- TTS 单节点：继续写 `ScriptNode.audio_url/audio_duration`，失败返回现有统一响应。
- TTS 批量：继续用 `tts_generation_status` 和 `ScriptNode.audio_url/audio_duration`，后续再考虑持久化。
- 声音复刻：继续写 `TeacherAsset.clone_status/clone_voice_id/updated_at`。

中期可考虑统一任务表，但不在 8 月决赛前实施。

## 对 8 月决赛的风险评估

R2A 本身只新增文档，不改变运行行为，风险低。

后续 R2B 风险集中在：

- 数字人生成状态不能误标完成。
- PPT 超时、业务失败不能被同步接口误报成功。
- 前端轮询和同步调用结构不能变化。
- 外部服务 fake 和生产 client 的注入点不能被破坏。

因此 R2B 必须先跑 M4A/M4B/R1 关键回归和前端 build。

## 对 9 月计算机垂类的复用价值

9 月若进入计算机垂类，可能出现代码执行、判题、可视化渲染、运行日志收集等长任务。R2 的复用价值是：

- 用统一 `TaskStatus` 描述运行、成功、失败、超时、部分成功。
- 用 `TaskContext` 记录 course/node/user/provider 等上下文。
- 用 `TaskResult` 区分网络失败、业务失败、响应异常和超时。
- 用 fake 支持无需真实外部沙箱或付费服务的自动化测试。

但本阶段不实现 `CODE_EXECUTION`，不创建占位 endpoint，不实现计算机垂类功能。
