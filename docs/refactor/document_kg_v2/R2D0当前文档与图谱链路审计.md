# R2D0 当前文档与图谱链路审计

## 1. 审计结论

当前生产主链是“上传接口内同步解析、同步落库、同步生成脚本，随后启动后台 TTS”。它不是一个持久化的文档流水线，也没有形成可版本化、可追溯的教育知识图谱。

证据口径只采用注册路由、实际调用、模型和测试：

- 已接入主链：`document.py:364 upload_document`、`DocumentService.process_document`、`ScriptGenerator`、`RAGProcessor`、`Course/DoclingDocument/CourseScript/ScriptNode`。
- 有代码但主链未调用：`KnowledgeExtractor.extract_knowledge_points`、`common/ppt_parser.py:PPTParser`、知识库文档导入。
- 仅占位：`models/knowledge_graph.py`、`schemas/graphrag.py`、`api/v1/endpoints/graphrag.py`、`engine/graphrag/__init__.py` 只有注释，且未发现注册路由。
- 历史/旁路：`KnowledgeSearchService` 是数据库 `contains` 搜索；`KnowledgeImportService` 可从当前 RAG 树递归创建知识点，但上传主链不调用。

## 3. 主链中的数据事实

1. `DocumentParser` 每次解析构造 Docling converter，任何 Docling 异常都进入格式级 fallback。
2. Docling 的结构先被导出为 Markdown，再由 `StructureParser` 用标题正则重建；原生 block 类型、坐标、阅读顺序和 provenance 没有成为稳定中间表示。
3. 上传落库只创建 `DoclingGroup` 和 `DoclingText`；虽然模型定义了 `DoclingTable`、`DoclingTableCell`、`DoclingPicture`，主链未持久化这些对象。
4. `process_document` 的主序是 parse -> structure -> script -> RAG；`KnowledgeExtractor` 不在此序列。
5. `RAGPipeline` 的 `_processed_docs` 和 `TreeRAGRetriever._index` 都在内存；`build_index` 会清空并替换索引，所以不是多课程知识库。
6. `document_cache` 同样是模块级内存字典，进程重启即丢失。

## 5. 可复用与应替换边界

可复用：`Course/ScriptNode` 兼容输出、TaskRunner 结果语义、Docling 现有 provider、LibreOffice/PDF 渲染、原生 `python-pptx` 提取逻辑、M4/M7 契约测试、现有 page mapping 作为 V1 fallback。

应替换为 V2 默认：Markdown 正则作为唯一结构源、全局可变 RAG 索引、单次 prompt 直接生成知识结构、无证据的自由字符串关系、上传路由内的一体化解析编排。

必须保留回滚：现有 `upload_document -> DocumentService -> ScriptNode` 行为在 M7 冻结期继续作为 V1；V2 先 shadow，不能直接覆盖 V1 表和缓存。

## 6. 测试缺口

- `test_m4b_main_flows.py:234` 与 `test_m7_demo_flow.py:94` 均 fake `process_document`，证明接口流程但不证明真实解析质量。
- 未发现覆盖真实 PPTX/PDF/DOCX parser、扫描件 OCR、表格/公式、阅读顺序、跨课程 RAG 隔离的专门基准测试。
- 现有映射测试偏业务逻辑和 mock，没有以人工标注 block/page 为真值。

结论：R2D0 必须先建立可比较的 DocumentIR、ParserProvider contract、证据和评测基线，再替换 parser 或图算法。
