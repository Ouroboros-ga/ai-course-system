# 产品二：CodeNexus 计算机学科智能教学系统

建议对外名称：**CodeNexus·智码交响：面向高校程序设计与算法学习的可验证智能导师**。

产品阶段：9 月后续产品规划。本文是完整功能设计、能力清单和实施路线；除明确标为“平台复用已完成”的部分外，**产品二特有能力当前均未在仓库主链实现**。

## 1. 产品目标、范围与关系

### 1.1 要解决的问题

产品一解决“如何把课程建设出来并支持学习”。产品二进一步解决“学生为什么在程序设计和算法中做错、如何得到可验证的指导、教师如何理解班级错误分布”。

```text
学生的概念问题 / 代码提交 / 练习结果
-> 学科资料和题目约束
-> 隔离编译、执行、测试与静态分析
-> 结构化错误、执行事件和来源证据
-> 分层提示、补学、再验证
-> 教师可复核的学情汇总
```

### 1.2 首期学科范围

首期只覆盖：

- Python 与 C++ 基础程序设计；
- 数组、链表、栈、队列、树、图；
- 排序、查找、递归、回溯、BFS、DFS、最短路径；
- 复杂度、边界条件、循环不变量和常见错误模式。

首期不覆盖整个计算机学科，不把一般聊天助手包装成垂类教学系统，也不在主 FastAPI 进程执行不可信学生代码。

### 1.3 与产品一的关系

| 层级 | 产品一提供的通用底座 | 产品二新增的垂类能力 |
|---|---|---|
| 课程与用户 | 账号、角色、课程、选课、素材、发布 | 课程的编程题、测试用例、错误案例和学科资源 |
| 学习体验 | 播放器、进度、问答、测验、前置跳转 | 代码编辑/提交、执行结果、分层诊断、算法可视化 |
| 资料与检索 | 课程资料处理与后续 DocumentIR 设计 | 编程语言规范、教材、题目、用例和错误模式的受控知识库 |
| 工程治理 | adapter、TaskRunner、fake、回归、M7 降级 | 隔离执行安全、资源限额、结果审计、题集与对照轨迹评测 |

产品二不替换产品一；它只复用已验证的平台能力，并以独立的安全、资料和算法证据来证明新增价值。

## 2. 用户、工作台与主流程

### 2.1 学生工作台

学生需要在一个学习面板完成：

1. 查看课程资料、概念讲解和练习目标。
2. 在代码编辑区编写或上传指定语言代码。
3. 提交后查看编译、运行、测试、异常和输出对比。
4. 在侧边对话区获得按层级控制的提示，而不是直接泄露答案。
5. 查看数组、树、图、调用栈等真实执行轨迹的可视化。
6. 在错误或测验失败后跳转补学，并重新运行验证。

### 2.2 教师工作台

教师需要能够：

1. 建立课程资料、编程题、样例、隐藏/公开测试用例和评分规则。
2. 审核知识来源、错误模式、提示模板和可视化标准轨迹。
3. 查看题目通过率、编译/运行错误、常见错误模式、提示依赖和知识点薄弱分布。
4. 选择补讲材料、布置下一练习或人工复核异常诊断。
5. 配置课程级安全策略、可见资料和对话边界。

### 2.3 主学习闭环

```text
教师配置资料、题目、测试和标准轨迹
-> 学生学习概念并提交代码
-> Code Runner 在隔离环境执行
-> 产出编译/运行/测试/静态分析结果
-> 诊断服务关联题目约束、错误模式和资料证据
-> 侧边对话按提示层级帮助学生修正
-> 再次提交并验证
-> 教师看到可复核的学习证据和班级聚合
```

## 5. 关键功能设计

### 5.1 隔离 Code Runner

Code Runner 必须是独立受限执行环境，而非 FastAPI 内 `exec`、子进程直跑或共享宿主目录。最小输入输出契约：

```text
输入：language, source_code, exercise_id, submission_id, resource_limits
输出：compile_status, run_status, exit_code, stdout, stderr,
      test_summary, duration_ms, memory_bytes, artifact_refs
```

必须处理 `success`、`compile_error`、`runtime_error`、`test_failed`、`timeout`、`resource_limit`、`service_unavailable`、`unexpected_exception`。错误输出不得泄露主机路径、密钥、隐藏测试或其他学生数据。

### 5.2 代码诊断与分层提示

诊断优先级应为：确定性结果 -> 题目约束 -> 已审核错误模式 -> 有来源的资料解释 -> 模型组织语言。模型只负责解释与追问，不能伪造运行结果。

| 层级 | 面向学生的内容 | 解锁条件 |
|---|---|---|
| L1 概念提醒 | 相关概念、前置条件、复杂度或边界问题 | 首次失败或主动请求 |
| L2 定位提示 | 相关函数、变量、测试类别或轨迹事件 | 学生已尝试且 L1 后仍失败 |
| L3 策略提示 | 处理步骤、伪代码片段或不变量检查 | 学生解释当前思路或再次失败 |
| L4 复盘解释 | 错误原因、改正方案、与资料的联系 | 题目完成、教师允许或达到明确阈值 |

### 5.3 真实执行轨迹、可视化与第一次分歧

首期事件集可限制为：`COMPARE`、`SWAP`、`POINTER_MOVE`、`RANGE_UPDATE`、`PUSH`、`POP`、`ENQUEUE`、`DEQUEUE`、`VISIT_NODE`、`UPDATE_DISTANCE`、`CALL_FUNCTION`、`RETURN_FUNCTION`、`BACKTRACK`。

流程如下：

```text
学生程序真实执行
-> 受限事件采集
-> 可视化状态序列
-> 与题目允许的标准轨迹集合对齐
-> 找到第一处不满足不变量/约束的事件
-> 关联代码位置、测试、知识点和资料证据
-> 给出 L1-L4 提示并允许再次验证
```

“第一次分歧”不能简单比较每一步变量是否和单份参考代码完全相同；必须先定义不变量、合法状态和等价实现，否则会误伤正确代码。

### 5.4 学科资料、知识结构与可追溯问答

拟建节点包括：`ProgrammingConcept`、`DataStructure`、`Algorithm`、`LanguageFeature`、`CodePattern`、`ErrorPattern`、`Complexity`、`TestCase`、`ProgrammingExercise`、`CompilerError`、`RuntimeError`、`Misconception`。

拟建关系包括：`IMPLEMENTS`、`USES`、`REQUIRES`、`HAS_COMPLEXITY`、`HAS_PRECONDITION`、`CAUSED_BY`、`FIXED_BY`、`TESTS`、`HAS_TEST_CASE`、`PREREQUISITE_OF`、`SUPPORTED_BY`、`APPEARS_ON`。

每个正式节点、关系、诊断和答案都必须可指向资料块、题目、测试或运行证据。没有可靠证据时，系统应说明无法确认，不得伪造引用。

### 5.5 学习证据、个性化与教师学情

首期仅建立可解释证据模型，不引入 BKT/HMM/LSTM：

- 稳定信息：学生自填或教师配置的课程/语言基础/无障碍偏好。
- 学习事件：阅读、播放、问答、测验、提交、测试、提示、跳转和复盘。
- 练习状态：每题语言、版本、结果、失败类别、提示层级和人工标记。
- 教师聚合：按题目、错误模式、知识点、班级和时间段统计，保留回溯原始证据入口。

任何“薄弱点”必须说明依据是哪些事件、是否存在样本不足或不确定性；不得把行为日志包装成对心理或认知状态的确定判断。

### 5.6 三个教学角色的后续设计

三个角色是产品交互职责，不是当前要实现的复杂多智能体框架：

| 角色 | 主要职责 | 可读取状态 | 允许写入 |
|---|---|---|---|
| 主导学角色 | 概念讲解、学习路径、提示层级和补学建议 | 课程资料、知识点、学习事件、已审核诊断 | 学习建议和策略理由 |
| 代码诊断角色 | 解释编译、测试、AST、轨迹和错误模式 | 题目、代码、Runner 结果、资料证据 | 结构化诊断与代码证据引用 |
| 工程学习角色 | 管理项目/实验阶段、提交规范和协作任务 | 项目要求、提交历史、教师规则 | 项目进度与风险提醒 |

运行原则：简单概念问题由主导学角色处理；代码问题由代码诊断角色主导；工程问题由工程角色主导；综合问题由一个明确主导角色汇总共享证据。不得让多个角色互相竞争、投票或无边界写入同一记忆。

## 6. 分阶段实施路线

| 阶段 | 目标 | 修改范围 | 完成标准 | 回滚原则 |
|---|---|---|---|---|
| P0 题目与安全执行 | 一个语言、少量固定题型的提交-执行-结果闭环 | 独立 runner 边界、题目/提交数据、最小 UI | 隔离、安全、超时、单测和错误结果可重复验证 | 关闭垂类入口，不影响产品一 |
| P1 垂类资料与诊断 | 将题目、资料、错误模式与确定性结果关联 | R2D 兼容资料结构、诊断 schema、教师审核 | 每条诊断有运行/资料证据，能拒答 | 退回仅显示 Runner 原始结果 |
| P2 轨迹与可视化 | 支持有限算法的真实轨迹和动画 | 事件采集、可视化组件、对照集 | 轨迹一致、等价正确实现不误报 | 关闭可视化，仅保留执行结果 |
| P3 学情与角色 | 可解释的教师聚合和单主导角色协作 | 学习事件、教师视图、角色策略 | 可回溯、可删除、教师可覆盖 | 退回静态报表/单一问答 |

每一阶段必须新增单元、集成、隔离/安全和人工验收记录；不得通过 skip、fake 成功或删除失败案例获得“完成”。

## 7. 验收、风险与禁止项

### 7.1 关键验收指标

| 维度 | 必须证明的事实 | 不可伪造的指标 |
|---|---|---|
| 安全 | 不可信代码不能访问宿主网络、文件、密钥或其他任务 | 沙箱逃逸、资源限制和异常恢复测试结果 |
| 正确性 | 编译/运行/单测结果可重复，诊断能回到确定性证据 | 题集通过率、误诊率、等价实现误报率 |
| 可追溯 | 问答和诊断可定位到资料、题目、代码、用例或事件 | 引用覆盖率和人工抽样核验 |
| 教学价值 | 提示与补学帮助学生再次独立验证 | 对照组/人工评价，不能只看模型自评 |
| 可运维 | 超时、不可用、业务失败均可解释、可恢复 | 故障演练和回滚记录 |

### 7.2 主要风险

1. 代码执行安全风险最高，必须先有隔离环境和红队测试。
2. 单参考轨迹会误判等价正确算法，必须以合法状态/不变量设计对照集。
3. LLM 可能编造错误原因或来源，因此工具结果与资料证据必须优先。
4. 代码和学习事件具有隐私与学术诚信风险，必须最小化采集、明确授权和提供删除机制。
5. 产品一的文档/RAG 主链仍在重构设计期，产品二不能抢跑依赖未验证的图谱或检索能力。

### 7.3 明确禁止项

- 不能把 `codebench.py`、`graphrag.py`、`cognitive.py`、`agents.py` 等占位文件当作实现。
- 不能在当前阶段实现或宣传 BKT、HMM、LSTM、GraphRAG 或复杂多智能体。
- 不能在主应用进程运行学生代码，不能调用真实付费模型来替代自动化测试。
- 不能宣称准确率、性能、教学效果或真实部署稳定性，除非有可复现评测和人工记录。
- 不能让自动诊断、评分或角色建议取代教师最终裁量。
